第4回-3：REST APIの基本 – エンドポイントと『資源』の考え方

🔌 REST APIとは?

REST API = システム同士が会話するための「窓口」
決まった形でお願いできる入口
Webの設計ルールに則った、標準的な仕組み

💡 コンビニのレジのイメージ

コンビニに行ったとき、「商品を渡す→お金を払う→レシートをもらう」という決まった流れがありますよね。

この「レジ」がまさにAPI。
裏側でどんな在庫管理システムが動いているかは客には見えないけれど、
レジという「窓口」を通じて、決まった形でやり取りができる。

なぜAPIが必要なのか?

🔒
1. 安全性
直接データベースにアクセスするのは危険。

APIを通せば、「この操作だけは許可」「この範囲のデータだけ見せる」という制御ができる。

銀行のATMと同じ役割。
♻️
2. 再利用性
一度APIを作っておけば、Webサイトからも、スマホアプリからも、社内の別のシステムからも、同じAPIを使える。

それぞれのシステムごとに別々の仕組みを作る必要がない。
💪
3. 変更への強さ
データベースの構造を変更しても、API自体の見た目はそのままにできる。

使う側のシステムは何も変更しなくていい。

長く保守していく上で重要なポイント。

🎯 RESTについて

次に「REST」についてです。RESTは「REpresentational State Transfer」の略で、これはWebの設計ルールの一種です。ただ、この正式名称を覚える必要は全くありません。非エンジニアの方は「RESTって、APIを作るときの設計のお作法なんだな」くらいに思っていただければ十分です。

RESTが生まれた背景

RESTという考え方が生まれたのは2000年のことです。当時、Web上でシステム同士がデータをやり取りする方法は、複雑で統一感がありませんでした。それぞれの会社、それぞれのシステムが、バラバラの方法でAPIを作っていたんです。

そこで、ロイ・フィールディングという研究者が、「Webの仕組みをうまく活用して、シンプルで分かりやすいAPI設計のルールを作ろう」と提案しました。それがRESTです。

RESTの最も重要なポイント

「URLの形を見れば、何をお願いしているか分かる」
例えば、/customersというURLを見たら、
「ああ、これは顧客に関するお願いだな」と分かる。

/ordersなら「注文に関することだな」と分かる。
/productsなら「商品についてだな」と分かる。

こういう風に、URLそのものが「意味を持つ」ように設計するのが、RESTの大きな特徴なんです。

💡 リソース指向という考え方

これを「リソース指向」と言います。リソースとは「資源」という意味ですが、ここでは「扱いたいデータのまとまり」と考えてください。

RESTが登場する前は、例えば/getCustomerListとか/updateCustomerInfoとか、動詞を含んだURLが多かったんです。

でもRESTでは、URLには名詞(リソース名)だけを使って、動詞はHTTPメソッド(GET、POSTなど)で表現します。

この統一ルールのおかげで、初めて見るAPIでも「ああ、だいたいこういう構造だろうな」と予測できるようになりました。これがRESTの大きなメリットなんです。

📌 まとめ

REST APIとは、
「Webの設計ルールに則った、システム同士が会話するための窓口」

非エンジニアの皆さんにとって重要なのは、
「このAPI、何ができるの?」「どういうお願いができるの?」
ということを理解できるようになること

非エンジニアにとってのAPIリテラシー

コードを書く必要はありません。でも、「ああ、このAPIはこういう形でお願いできるんだな」というイメージを持てるようになると、エンジニアとの会話が格段にスムーズになります。

例えば、社内で新しいシステムを導入するとき、ベンダーから「このシステムはREST APIを提供しています」と言われたとします。そのとき、皆さんが「ああ、じゃあ他のシステムとの連携もしやすいですね」「どんなエンドポイントがありますか?」と質問できる。これが、非エンジニアにとってのAPIリテラシーなんです。

また、社内でシステム開発を企画するとき、「このシステムには外部連携用のREST APIを用意してほしい」と要件に入れることもできます。将来的な拡張性を考えた設計を、最初から求められるわけです。

このように、REST APIの基本を理解することは、非エンジニアの皆さんが、システム企画や運用に関わる上で、非常に重要なスキルになっているんです。

📍 エンドポイントとリソースのイメージ

エンドポイント = APIにお願いするときのURL

郵便を送るときの宛先住所と同じ。
「この住所にお願いを届ける」というイメージ

顧客管理システムのAPI例

GET
/customers
📖 顧客の一覧をください
システムに登録されているすべての顧客のデータが返ってくる。
完全なURLで書くと: https://api.example.com/customers

通常はページング(ページ分け)を使って、少しずつデータを取得する。
GET
/customers/123
🔍 ID番号が123番の顧客の情報をください
/customersの後ろに/123と付いている。
この123は顧客ID、つまり特定の一人を指定している。

このような形を「パスパラメータ」と呼ぶ。
第2回で学んだ「主キー」に対応している。
POST
/customers
➕ 新しい顧客を登録してください
同じ/customersというエンドポイントでも、
HTTPメソッドを変えるだけで、操作の意味が変わる

GETなら「見せて」、POSTなら「登録して」
これがRESTの面白いところ!
💎 リソース(資源)という考え方
リソース = 「扱いたいデータのまとまり」

/customersのcustomersがリソース名
同様に、/ordersなら注文リソース、/productsなら商品リソース

RESTでは、リソース名はそのままで、メソッドを変えることで操作を変える

• GETなら「見せて」
• POSTなら「作って」
• PUTなら「更新して」
• DELETEなら「消して」

🔄 REST API と SQL の対応関係

GET
/customers
📖 顧客の一覧を取得
SELECT * FROM customers;
GET
/customers/123
🔍 ID が 123 の顧客を取得
SELECT * FROM customers
WHERE id = 123;
💡 パスパラメータ 123 が SQL の WHERE 句になる
POST
/customers
➕ 新しい顧客を登録
INSERT INTO customers
(name, email, prefecture, ...)
VALUES ('田中太郎', 'taro@example.com', '石川県', ...);
💡 リクエストボディの内容が SQL の VALUES になる
PUT
/customers/123
✏️ ID が 123 の顧客情報を更新
UPDATE customers
SET name = '田中太郎',
    email = 'new@example.com'
WHERE id = 123;
DELETE
/customers/123
🗑️ ID が 123 の顧客を削除
DELETE FROM customers
WHERE id = 123;
💡 実務では、完全削除ではなく削除フラグを立てることが多い
UPDATE customers SET is_deleted = TRUE WHERE id = 123;

📌 ここで押さえておきたいポイント

1️⃣ エンドポイント = 「どのリソースを扱うか」を示すURL
/customers なら顧客の話、 /orders なら注文の話
2️⃣ HTTPメソッド = 「どんな操作をするか」を示す動詞
GET(取得)、POST(作成)、PUT(更新)、DELETE(削除)
3️⃣ REST API と SQL の本質は同じ
SQLは「データベースに直接命令する言葉」
APIは「外部から安全にお願いするための窓口」
言葉は違うけど、やっていることは同じ!
非エンジニアの皆さんが覚えておくべきこと:

「エンドポイントを見れば、大体何の話をしているか分かる」

/customers なら顧客の話、 /orders なら注文の話
URL自体が意味を持つ。これがRESTの大きな利点!

📋 エンドポイントの命名慣習

1️⃣ リソース名は複数形にする
/customerではなく/customers
/orderではなく/orders

「顧客の集まり」「注文の集まり」というニュアンスを表す
2️⃣ 動詞を使わない
/getCustomersとか/createOrderではなく、
/customers、/ordersという名詞だけにする

動詞はHTTPメソッドで表現するから
3️⃣ 階層構造を使う
「顧客IDが123の人の注文一覧」を取得したい場合:
/customers/123/orders

「顧客123の下にある注文たち」という階層関係をURL構造で表現

💼 経営・業務視点でのAPI例

顧客管理システムで必要になりそうな操作を
REST API風に表現すると...

GET
/customers

1️⃣ 顧客一覧の取得

📋 目的
登録されている顧客全員の一覧を取得する操作。
営業担当者が「今日訪問する顧客リスト」を見たいとか、マーケティング部門が「全顧客のデータを分析したい」といった場合に使います。
💡 ページング機能
何千人、何万人もいると大変なので、「1ページ20件」といったページング機能を付けることが多いです。
その場合は、クエリパラメータを使います。
GET /customers?page=1&limit=20
👉 「1ページ目を、1ページあたり20件で取得してください」という意味
🔍 条件絞り込み
クエリパラメータを使うことで、柔軟な検索ができます。
GET /customers?prefecture=石川県&status=契約済み&page=1
👉 「石川県の、ステータスが契約済みの顧客を、1ページ目から取得する」

実務では、「どんな条件で絞り込みたいか」を事前に洗い出しておくことが重要です。
都道府県? 業種? 契約日? 売上規模? こういった業務要件を整理して、
「このパラメータが必要です」とエンジニアに伝えられるようになると、非常にスムーズです。
GET
/customers/{id}

2️⃣ 顧客詳細の取得

📋 目的
{id} というのは、「顧客IDが入る」という意味です。
実際には、GET /customers/123 や GET /customers/456 という形になります。

これで、特定の一人の顧客について、名前、住所、電話番号、メールアドレス、会社名、担当者、契約日、購入履歴など、詳しい情報をすべて取得できます。
💼 使用シーン
• 営業担当者が「この顧客、前回いつ訪問したっけ?」「どんな商品を買ってたっけ?」と確認したいとき
• カスタマーサポートが電話対応中に「お客様の情報を確認させてください」と言って、詳細情報を表示する
POST
/customers

3️⃣ 新規顧客の登録

📋 目的
新しい顧客をシステムに登録する操作。
名前や住所などの情報を、リクエストの中に含めてサーバーに送ります。
具体的には、JSON形式でデータを送ることが多いです。
📤 リクエスト例(JSON形式)
{
  "name": "田中太郎",
  "email": "taro.tanaka@example.com",
  "phone": "090-1234-5678",
  "prefecture": "石川県",
  "company": "株式会社サンプル"
}
📥 レスポンス例
登録が完了すると、「登録しました。新しい顧客のIDは123番です」という情報が返ってきます。
この返ってきたIDを使って、さらに詳細情報を取得したり、更新したりできるわけです。
💡 実務のポイント
「必須項目は何か」「任意項目は何か」を明確にすることが大事です。
例えば、名前とメールアドレスは必須だけど、電話番号は任意、といった具合です。
これをAPI仕様書に明記しておくと、フロントエンドの開発者が「この項目は入力必須だな」と分かります。
PUT
/customers/{id}

4️⃣ 顧客情報の更新

📋 目的
既存の顧客情報を更新する操作。
例えば、ID=123の顧客の住所が変わったら、PUT /customers/123 というエンドポイントに、新しい住所情報を含んだデータを送ります。
📤 リクエスト例
{
  "address": "石川県金沢市◯◯町1-2-3",
  "phone": "090-9999-8888"
}
👉 変更したい項目だけを送ることもできますし、すべての項目を送ることもあります。これは設計次第です。
💡 PUT vs PATCH
PUT と似たメソッドに PATCH というものもあります。

• PUT:「全体を置き換える」イメージ
• PATCH:「一部だけ変更する」イメージ

実務では、この使い分けはケースバイケースなので、チーム内で統一ルールを決めておくといいでしょう。
PUT
/customers/{id}/status

5️⃣ 顧客ステータスの変更(専用エンドポイント)

📋 目的
顧客全体の情報を更新するのではなく、「ステータスだけ」を変更したい場合、専用のエンドポイントを用意することもあります。

例えば、営業プロセスで「見込み客」→「商談中」→「契約済み」→「休眠」といったステータスがあるとして、それを変更する専用のAPIを作るわけです。
📤 リクエスト例
{
  "status": "契約済み"
}
👉 PUT /customers/123/status に送ると、
ID=123の顧客のステータスだけが「契約済み」に変わります。
💡 なぜ専用エンドポイントを作るのか?
• ステータス変更という操作が頻繁に行われる場合、専用APIがあった方が使いやすい
• ステータス変更のときだけ特別なログを残したい
• ステータス変更時に通知を飛ばしたい、といった追加処理がある場合

専用エンドポイントがあると実装しやすくなります。
POST
/customers/{id}/notes

6️⃣ 顧客へのメモ追加

📋 目的
顧客情報の一部として「メモ」を追加する専用のAPI。
営業担当が「◯月◯日に電話した」「次回フォローは来週」「A商品に興味あり」といったメモを残せると便利ですよね。
📤 リクエスト例
{
  "content": "2025年11月22日に電話。次回訪問は12月1日予定。",
  "author": "山田太郎"
}
👉 POST /customers/123/notes に送ると、
ID=123の顧客に新しいメモが追加されます。
💡 サブリソースという概念
このように、顧客というメインのリソースの下に、「ノート(メモ)」というサブリソースを配置する形になっています。

/customers/{id}/notes というURL構造が、
「顧客の下にあるメモたち」という階層関係を表しているわけです。
GET
/customers/search

7️⃣ 顧客の検索(検索専用エンドポイント)

📋 目的
検索専用のエンドポイントを用意することもあります。
顧客一覧の取得(GET /customers)とは別に、複雑な検索条件を扱いたい場合、こういう形もあり得ます。
🔍 使用例
GET /customers/search?keyword=田中&prefecture=石川県
👉 フリーワード検索で「田中」と入力したら、
名前、会社名、メモの中から「田中」を含むすべての顧客を返す、といった機能です。
DELETE
/customers/{id}

8️⃣ 顧客の削除(無効化)

📋 目的
顧客を削除する操作。
ただし、実務では本当にデータを消すのではなく、is_deleted というフラグを立てるだけのことが多いです。
⚠️ 削除の実装方法
あるいは、削除ではなく「無効化」という表現を使うこともあります。
その場合、PUT /customers/{id}/deactivate のような専用エンドポイントを作ることもあります。
💡 実務のポイント
削除や無効化は、慎重に扱うべき操作なので、誤操作を防ぐために:

• 確認画面を挟む
• 管理者権限を要求する
• 削除ログを詳細に記録する

といった仕組みを組み合わせることが多いです。

📊 レポート・BI用途のAPI例

REST APIの考え方は、顧客や注文といった「モノ」を扱うだけでなく、
レポートや集計といった「情報」を扱うこともできるんです。

GET
/reports/monthly-sales
📈 月次の売上レポート
GET /reports/monthly-sales?year=2025&month=11
年と月を指定すると、その月の売上データが返ってくる。
これを、経営会議の資料作成に使ったり、ダッシュボードに表示したりできます。
GET
/reports/new-customers
👥 今月新規登録した顧客の数
GET /reports/new-customers?year=2025&month=11
このように、レポート専用のエンドポイントを作ることもあります。
GET
/reports/product-ranking
🏆 商品別の売上ランキング
GET /reports/product-ranking?year=2025&month=11&limit=10
上位10商品を取得する、といったこともできます。
💡 自動化が進む
実務では、「どんなレポートが定期的に必要か」を洗い出して、
それをAPI化しておくと、自動化が進みます。

毎月手作業でExcelに集計していた作業が、
「APIから自動でデータを取得してレポート生成」
というように変わるわけです。

🤖 AIに「API一覧」を作らせるデモ

それでは、ここからは実際にAIを使って、API設計を手伝ってもらうデモをお見せします。

今回の題材は、「問い合わせ管理システム」にしましょう。社内で顧客からの問い合わせを管理するシステムをイメージしてください。

📋 問い合わせ管理システムの機能

• 問い合わせの新規登録
• 問い合わせ一覧の取得(ステータスで絞り込めると便利)
• 問い合わせの詳細表示
• ステータスの変更(「未対応」→「対応中」→「完了」など)
• 担当者の割り当て
• メモの追加
❓ こんな状況を想定
これらの機能を、REST API風に設計したい。
でも、「どんなエンドポイントにすればいいのか分からない」「HTTPメソッドはどれを使えばいいのか分からない」という状況です。

💡 そんなとき、AIに業務内容と機能を伝えるだけで、
REST API風の一覧表を作ってくれる!

📝 プロンプト例
社内の「問い合わせ管理システム」のREST APIを設計したいです。 次のような機能があります: - 問い合わせの新規登録 - 問い合わせ一覧の取得(ステータスで絞り込み) - 問い合わせ詳細の表示 - ステータスの変更(対応中 → 完了など) - 担当者の割り当て - メモの追加 非エンジニアにもわかるように、 以下の項目を含めたAPI一覧を表形式で提案してください。 - HTTPメソッド - パス(エンドポイント) - 目的(日本語) - 主な入力項目 - 主な出力項目

✨ AIが返してくれるイメージ

表形式で、各APIのメソッド、エンドポイント、
入力項目、出力項目が整理されて返ってくる!

これを見ながら、
「この項目も必要だな」「こんなAPIもあった方がいいな」
と気づきを得ることができる。

No HTTPメソッド エンドポイント 目的 主な入力項目 主な出力項目
1 POST /inquiries 新しい問い合わせを登録 タイトル、内容、顧客名、メールアドレス、カテゴリー 問い合わせID、登録日時
2 GET /inquiries 問い合わせ一覧を取得 ステータス(未対応/対応中/完了)、ページ番号 問い合わせID、タイトル、ステータス、登録日時、担当者名の配列
3 GET /inquiries/{id} 特定の問い合わせの詳細を取得 なし(URLのIDのみ) 問い合わせの全情報(タイトル、内容、顧客情報、ステータス、メモ一覧など)
4 PUT /inquiries/{id}/status 問い合わせのステータスを変更 新しいステータス(未対応/対応中/完了) 更新後のステータス、更新日時
5 PUT /inquiries/{id}/assign 担当者を割り当て 担当者ID 担当者名、割り当て日時
6 POST /inquiries/{id}/notes メモを追加 メモの内容、記入者ID メモID、記入日時
✨ このようにAIが表形式で整理して提案してくれる
これを見ながら、
「この項目も必要だな」「こんなAPIもあった方がいいな」
と気づきを得て、ブラッシュアップしていきます。
💡 AIが作ったAPI一覧、次にどうする?
1. 「この一覧、うちの業務に合ってるかな?」とチェックする
例えば、「問い合わせの削除」の機能が抜けてるかもしれません。
あるいは、「カテゴリーごとに集計したい」という要望があるなら、GET /inquiries/summary?category=商品みたいなAPIが追加で必要かもしれません。
2. 足りないものがあれば、AIに追加依頼する
「こういう機能も欲しいんですが、エンドポイントを追加してください」とお願いすればいいんです。

例えば:
この一覧に、以下の機能も追加したいです。 - 問い合わせの削除(論理削除) - カテゴリー別の集計(各カテゴリーの件数を取得) - 担当者別の問い合わせ一覧(特定の担当者が抱えている問い合わせを取得) これらのエンドポイントも提案してください。
こんな風にAIに追加で依頼すれば、さらに表が充実します。
3. エンジニアとの打ち合わせの材料にする
この一覧を見ながら、
「このAPI一覧で、うちの業務はカバーできますか?」
「ステータスの変更は専用エンドポイントがいいですか、それとも全体の更新でまとめた方がいいですか?」
といった具体的な会話ができるようになります。

これが、非エンジニアのAPI設計への関わり方です。コードは書けなくても、
「どんな機能が必要で、どんな形で提供されるべきか」を整理することはできるんです。
4. さらにAIに質問して、理解を深める
このAPI一覧を使って、さらに具体的な質問ができます。

例えば:
この「問い合わせ一覧取得」のAPI、
ステータスが「未対応」のものだけを取得したい場合、
具体的にどんなURLになりますか?
とか、
「メモ追加」のAPIで送るデータは、
どんな形式(JSON)で送ればいいですか?
サンプルを見せてください。
といった質問をAIにすることで、より具体的な理解が深まります。
5. セキュリティや設計の注意点を聞く
このAPI設計で、セキュリティ上注意すべき点はありますか?
と聞けば、AIが「担当者の権限チェックが必要です」「メモの記入者IDは、ログインユーザーのIDと一致するか確認すべきです」といったアドバイスをくれるかもしれません。

こんな風に、AIは「設計のたたき台を作る相棒」として、非常に強力なツールになるんです。
⚠️ 重要: AIが作ったものを鵜呑みにしない
AIは業務の細かい事情までは知りません。

「うちの会社では、問い合わせの担当者は複数人アサインできるようにしたい」
「カテゴリーは3階層の構造になってる」

そういう独自ルールは、皆さんが補足する必要があります。

AIが作った叩き台を見て、「ここは違うな」「これが足りないな」と気づけること。
そして、それをAIにフィードバックして修正してもらうこと。

これが、AIディレクターとしてのスキルなんです。
AIは「完璧な答え」を出してくれるわけではありません。
でも、「80点の叩き台」を一瞬で作ってくれます。

それを、皆さんの業務知識で「95点」に仕上げる。

これが、これからの仕事の進め方なんです。

📝 REST APIのまとめ

1
REST APIとは
システム同士が会話するための「窓口」
Webの設計ルールに則った、標準的な仕組み

安全性・再利用性・変更への強さが特徴
2
エンドポイントとリソース
エンドポイント = APIにお願いするときのURL
リソース = 扱いたいデータのまとまり

リソース名はそのままで、メソッドを変えることで操作を変える
3
業務視点でのAPI設計
「どんな操作が必要か」を洗い出すことから始める

一覧取得、詳細取得、新規登録、更新、削除、ステータス変更、メモ追加...
4
AIとの協働
AIに業務内容を伝えるだけで、API一覧の叩き台を作ってくれる

それをブラッシュアップする。
これが、これからの非エンジニアの働き方

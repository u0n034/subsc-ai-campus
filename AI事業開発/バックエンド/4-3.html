第4回-3：REST APIの基本 – エンドポイントと『資源』の考え方

🔌 REST APIとは?

REST API = システム同士が会話するための「窓口」
決まった形でお願いできる入口
Webの設計ルールに則った、標準的な仕組み

💡 コンビニのレジのイメージ

コンビニに行ったとき、「商品を渡す→お金を払う→レシートをもらう」という決まった流れがありますよね。

この「レジ」がまさにAPI。
裏側でどんな在庫管理システムが動いているかは客には見えないけれど、
レジという「窓口」を通じて、決まった形でやり取りができる。

なぜAPIが必要なのか?

🔒
1. 安全性
直接データベースにアクセスするのは危険。

APIを通せば、「この操作だけは許可」「この範囲のデータだけ見せる」という制御ができる。

銀行のATMと同じ役割。
♻️
2. 再利用性
一度APIを作っておけば、Webサイトからも、スマホアプリからも、社内の別のシステムからも、同じAPIを使える。

それぞれのシステムごとに別々の仕組みを作る必要がない。
💪
3. 変更への強さ
データベースの構造を変更しても、API自体の見た目はそのままにできる。

使う側のシステムは何も変更しなくていい。

長く保守していく上で重要なポイント。

📍 エンドポイントとリソースのイメージ

エンドポイント = APIにお願いするときのURL

郵便を送るときの宛先住所と同じ。
「この住所にお願いを届ける」というイメージ

顧客管理システムのAPI例

GET
/customers
📖 顧客の一覧をください
システムに登録されているすべての顧客のデータが返ってくる。
完全なURLで書くと: https://api.example.com/customers

通常はページング(ページ分け)を使って、少しずつデータを取得する。
GET
/customers/123
🔍 ID番号が123番の顧客の情報をください
/customersの後ろに/123と付いている。
この123は顧客ID、つまり特定の一人を指定している。

このような形を「パスパラメータ」と呼ぶ。
第2回で学んだ「主キー」に対応している。
POST
/customers
➕ 新しい顧客を登録してください
同じ/customersというエンドポイントでも、
HTTPメソッドを変えるだけで、操作の意味が変わる

GETなら「見せて」、POSTなら「登録して」
これがRESTの面白いところ!
💎 リソース(資源)という考え方
リソース = 「扱いたいデータのまとまり」

/customersのcustomersがリソース名
同様に、/ordersなら注文リソース、/productsなら商品リソース

RESTでは、リソース名はそのままで、メソッドを変えることで操作を変える

• GETなら「見せて」
• POSTなら「作って」
• PUTなら「更新して」
• DELETEなら「消して」

📋 エンドポイントの命名慣習

1️⃣ リソース名は複数形にする
/customerではなく/customers
/orderではなく/orders

「顧客の集まり」「注文の集まり」というニュアンスを表す
2️⃣ 動詞を使わない
/getCustomersとか/createOrderではなく、
/customers、/ordersという名詞だけにする

動詞はHTTPメソッドで表現するから
3️⃣ 階層構造を使う
「顧客IDが123の人の注文一覧」を取得したい場合:
/customers/123/orders

「顧客123の下にある注文たち」という階層関係をURL構造で表現

💼 経営・業務視点でのAPI例

顧客管理システムで必要になりそうな操作を
REST API風に表現すると...

メソッド エンドポイント 何をするAPIか
GET /customers 顧客一覧を取得(ページング・絞り込み可能)
GET /customers/{id} 特定の顧客の詳細情報を取得
POST /customers 新しい顧客を登録
PUT /customers/{id} 顧客情報を更新
PUT /customers/{id}/status 顧客ステータスを変更(専用エンドポイント)
POST /customers/{id}/notes 顧客へのメモを追加
DELETE /customers/{id} 顧客を削除(または無効化)

💡 重要なポイント

このAPIがあると、他のシステムとデータ連携しやすくなる!

• MAツールから顧客データを取りに来る
• 経営ダッシュボードでリアルタイムデータを表示
• スマホアプリで外出先から顧客情報を確認

APIはシステム同士をつなぐ「のり」のようなもの

APIがあることのメリット

🔗
システム連携が容易
MAツール、BIツール、会計システムなど、
他のツールとの連携がスムーズになる。

1日1回、夜中に自動でデータを同期する、
といった運用が可能に。
📱
マルチデバイス対応
Webブラウザからアクセスしても、
スマホアプリからアクセスしても、
同じAPIを使える。

これが再利用性の高さ。
⚡
自動化が進む
定期的に必要なレポートを、
APIから自動でデータを取得して生成。

毎月手作業でExcelに集計していた作業が、
自動化できる。
🏗️
将来の拡張性
後から新しいツールを導入したり、
データを別の用途で使い回したりするのが、
ずっと楽になる。

「API ファースト」の設計思想。

🤖 AIに「API一覧」を作らせるデモ

AIに業務内容と機能を伝えるだけで、
REST API風の一覧表を作ってくれる!

📝 プロンプト例
社内の「問い合わせ管理システム」のREST APIを設計したいです。 次のような機能があります: - 問い合わせの新規登録 - 問い合わせ一覧の取得(ステータスで絞り込み) - 問い合わせ詳細の表示 - ステータスの変更(対応中 → 完了など) - 担当者の割り当て - メモの追加 非エンジニアにもわかるように、 以下の項目を含めたAPI一覧を表形式で提案してください。 - HTTPメソッド - パス(エンドポイント) - 目的(日本語) - 主な入力項目 - 主な出力項目

✨ AIが返してくれるイメージ

表形式で、各APIのメソッド、エンドポイント、
入力項目、出力項目が整理されて返ってくる!

これを見ながら、
「この項目も必要だな」「こんなAPIもあった方がいいな」
と気づきを得ることができる。

💡 AIを使うポイント
1. 「非エンジニアにもわかるように」と明示する
難しい専門用語を避けて、分かりやすい説明をしてくれる
2. 出力形式を指定する
「表形式で」「次の項目を含めて」と具体的にお願いすると、欲しい形で回答が返ってくる
3. AIの回答を鵜呑みにしない
AIは業務の細かい事情までは知らない。「ここは違うな」「これが足りないな」と気づいて、フィードバックする
4. 叩き台として活用する
AIが作った「80点の叩き台」を、あなたの業務知識で「95点」に仕上げる

1
REST APIとは
システム同士が会話するための「窓口」
Webの設計ルールに則った、標準的な仕組み

安全性・再利用性・変更への強さが特徴
2
エンドポイントとリソース

リソース = 扱いたいデータのまとまり

3
業務視点でのAPI設計

4
AIとの協働
AIに業務内容を伝えるだけで、API一覧の叩き台を作ってくれる

それをブラッシュアップする。
これが、これからの非エンジニアの働き方

REST APIの基本を理解することは、
非エンジニアが、システム企画や運用に関わる上で、
非常に重要なスキルになっています。

コードは書けなくても、
「どんな機能が必要で、どんな形で提供されるべきか」を整理する
ことはできる!

### 2. HTTPとは？ – Webの「会話のルール」を知る（20分）

**目的：** URL・メソッド・ステータスコードの超ざっくりしたイメージを掴む

**2-1. Webアクセスで何が起きている？（URLの分解）（8分）**

* 実際のURLを画面に表示（例：`https://example.com/customers?pref=ishikawa`）

* URLをパーツに分解して解説

  * `https://` … 通信の方法（プロトコル）
  * `example.com` … サイトの住所（ドメイン）
  * `/customers` … サイトの中の「部屋」（パス）
  * `?pref=ishikawa` … 条件（クエリパラメータ）

* 比喩

  * 「建物（ドメイン）の中のどの部屋（パス）に、どんなお願い（クエリ）を届けるか」

* **AIデモ用プロンプト例** を紹介（画面で表示するだけでもOK）

  ```text
  このURLを分解して、それぞれが何を意味しているか、
  非エンジニアにもわかるように説明してください。
  URL: https://example.com/customers?pref=ishikawa
  ```

**2-2. HTTPメソッド – GETとPOSTの違いをざっくり（7分）**

* 「メソッド＝どういうお願いの種類か」と説明

  * GET：情報を「見せてください」
  * POST：新しい情報を「登録してください」
  * （名前だけ紹介）PUT / DELETE：更新・削除のイメージ
* ECサイトでの例

  * 商品一覧を見る → **GET**
  * 新規会員登録する → **POST**
* 「メソッドの違いを意識できるだけで、開発者との会話がスムーズになります」と強調

**2-3. ステータスコード – 200 / 404 / 500を理解する（5分）**

* よく見る3種類だけに絞って解説

  * 200：OK（うまくいきました）
  * 404：Not Found（ページが見つかりません）
  * 500：Server Error（サーバー側で問題が起きました）
* 社内システム運用のイメージ

  * 「500エラーが多発」→ バックエンド側の調査が必要
  * 「404が出る」→ URLの設定漏れ or デプロイミス など
* AIへの質問例を紹介

  ```text
  バックエンドのエラーログに「500 Internal Server Error」が
  出ているのですが、非エンジニアでもイメージできるように、
  どんなトラブルの可能性があるか教えてください。
  ```

### 3. REST APIの基本 – エンドポイントと「資源」の考え方（35分）

**目的：** REST APIの形・用語を押さえ、自社業務に当てはめる準備をする

**3-1. REST APIとは？（5分）**

* 用語紹介

  * REST：Webの「設計ルール」の一種（細かい定義には踏み込まない）
  * API：システム同士が会話するための「窓口」「インターフェース」
* 非エンジニア向けの一言定義

  * 「**他のシステムや画面から、決まった形で“お願い”できる入口**」

**3-2. エンドポイントとリソースのイメージ（10分）**

* スライドに例を表示

  * `GET /customers` … 顧客リストを取得
  * `GET /customers/123` … ID=123の顧客情報を取得
  * `POST /customers` … 新しい顧客を登録
* 「**/customers** という“資源（リソース）”に対して、GET/POSTなどで操作する」
* SQLとの対応関係を軽く示す

  * `GET /customers` ≒ `SELECT * FROM customers`
  * `POST /customers` ≒ `INSERT INTO customers ...`
* 第2回・第3回とのつながりを確認

  * 「第2回で作った**テーブル**が、RESTでは**リソース名**になってくるイメージです」

**3-3. 経営・業務視点でのAPI例（10分）**

* 顧客管理システムを例に

  * 顧客一覧取得：`GET /customers`
  * 顧客の詳細取得：`GET /customers/{id}`
  * 顧客のステータス変更：`PUT /customers/{id}/status`
  * 顧客のメモ追加：`POST /customers/{id}/notes`
* 「このAPIがあると、他のシステムと**データ連携しやすい**」と解説

  * MAツールとの連携
  * 自社ダッシュボードへのデータ取り込み など
* BI・レポート用途の例も軽く触れる

  * `GET /reports/monthly-sales` のようなAPIもあり得る

**3-4. AIに「API一覧」を作らせるデモ（10分）**

* 画面でAIに実際に投げる想定プロンプトを紹介

  ```text
  社内の「問い合わせ管理システム」のREST APIを設計したいです。

  次のような機能があります：
  - 問い合わせの新規登録
  - 問い合わせ一覧の取得（ステータスで絞り込み）
  - 問い合わせ詳細の表示
  - ステータスの変更（対応中 → 完了など）
  - メモの追加

  非エンジニアにもわかるように、
  以下の項目を含めたAPI一覧を表形式で提案してください。

  - HTTPメソッド
  - パス（エンドポイント）
  - 目的（日本語）
  - 主な入力項目
  - 主な出力項目
  ```

* AIの回答例を画面に表示し、ポイントを解説

  * 「こんな形でAPIの設計案を、まずAIに出させてからエンジニアと相談する、というスタイルが取れます」

### 4. JSONというデータ形式 – 「人にも機械にも読める」データの形（25分）

**目的：** JSONの見た目に慣れ、テーブルとの対応を理解する

**4-1. JSONの基本形を読む（10分）**

* シンプルなサンプルを表示

  ```json
  {
    "id": 123,
    "name": "田中太郎",
    "email": "taro.tanaka@example.com",
    "prefecture": "石川県",
    "is_active": true
  }
  ```
* 各部を説明

  * `{}` … 1人の顧客
  * `"id"` … 項目名（カラム名のようなもの）
  * `123` … 値（レコードの1行分の値）
  * 文字列 / 数値 / true/false などの違い
* 「**見た目はちょっと怖いけれど、実質は“名前付きの値のセット”**」と強調

**4-2. 配列とネスト – 複数件＆入れ子構造（8分）**

* 「顧客一覧」のJSON例

  ```json
  [
    {
      "id": 1,
      "name": "田中太郎"
    },
    {
      "id": 2,
      "name": "佐藤花子"
    }
  ]
  ```

  * `[]` … 「複数行の表」のイメージ
* ネスト構造の例（顧客＋複数の注文）も軽く紹介

  * 「第5回以降で、テーブル設計とセットでまた出てきます」と予告だけ

**4-3. JSON ↔ テーブルの対応をAIにやらせる（7分）**

* 第2回で扱ったような**顧客テーブル**の例を再利用

  * `customers` テーブル（id, name, email, prefecture…）

* AIにやらせるプロンプト例を紹介

  ```text
  次の顧客テーブルを、REST APIのレスポンスとして返すことを想定して、
  JSONのサンプルデータを3件分作ってください。

  - id（数値）
  - name（文字列）
  - email（文字列）
  - prefecture（都道府県名）
  - is_active（true/false）
  ```

* 「テーブル → JSON」への変換イメージを定着させる

  * 「非エンジニアは、JSONを“テーブルの別の見せ方”として捉えればOKです」

### 5. バックエンドがしていることを4ステップで言語化する（15分）

**目的：** フロントとDBの間で行われている処理を、シンプルなステップで説明できるようにする

**5-1. 4ステップモデルの提示（7分）**

* スライドで4ステップを表示

  1. **リクエストを受け取る**（URL・メソッド・JSONを受信）
  2. **内容を理解し、ビジネスルールを適用する**
  3. **データベースを操作する**（SQLを実行・結果を取得）
  4. **結果をJSONにまとめて返す**（レスポンス）
* 前の回とのリンク

  * 3番が第3回（SQL）の世界
  * 2番のビジネスルールは、第1回の「ビジネスロジック」に相当
* 非エンジニアの視点

  * 「**この4ステップで説明できれば、エンジニアとの会話はかなりスムーズになります**」

**5-2. 具体例で4ステップをなぞる（5分）**

* 例：`GET /customers?pref=ishikawa` のとき

  1. 「石川県の顧客一覧をください」というリクエストを受け取る
  2. 「pref=ishikawa を条件にする」というルールを決める
  3. `SELECT * FROM customers WHERE prefecture = '石川県';` を実行
  4. 取得した結果をJSONにして返す
* 図とテキストで流れを再掲し、イメージを強化

**5-3. AIに「処理の言語化」をさせるプロンプト例（3分）**

```text
次のAPIが裏側で行っている処理を、
非エンジニアにもわかるように4ステップで説明してください。

API:
GET /customers?pref=ishikawa
```

* 「**こういう説明をAIに作らせて、社内共有資料にする**」という使い方を提案

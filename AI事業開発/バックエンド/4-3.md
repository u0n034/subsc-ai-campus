# 第4回「REST APIの基本 – エンドポイントと『資源』の考え方」ナレーション原稿(拡充版)

## 3-1. REST APIとは?(5分)

それでは、ここから本格的にREST APIの話に入っていきましょう。

まず、「REST API」という言葉ですが、これは2つの言葉が組み合わさっています。「REST」と「API」です。順番に見ていきましょう。

まず「API」から説明します。APIとは「Application Programming Interface」の略です。日本語にすると「アプリケーション・プログラミング・インターフェース」となりますが、これだけ聞いても「何のこっちゃ?」という感じですよね。

非エンジニア向けに一言で言うと、APIとは**「他のシステムや画面から、決まった形でお願いできる入口」**のことです。

もう少し具体的に言うと、例えば皆さんの会社に顧客管理システムがあったとします。このシステムには、顧客のデータがたくさん入っていますよね。名前、住所、電話番号、購入履歴などなど。

で、この顧客データを、別のシステム、例えばマーケティングツールとか、経営ダッシュボードとか、そういった他のシステムからも使いたいとします。そのとき、どうやってデータをやり取りするか。これがAPIの出番なんです。

APIがあると、「顧客一覧をください」とか「この顧客の詳細情報をください」とか、決まった形でお願いできるんですね。システム同士が会話するための「窓口」「インターフェース」と考えてください。

APIを日常生活に例えると、コンビニのレジのようなものです。コンビニに行ったとき、皆さんは店員さんに「これください」と商品を渡しますよね。すると店員さんは決まった手順でバーコードをスキャンして、お金を受け取って、レシートを渡してくれます。

この「商品を渡す→お金を払う→レシートをもらう」という決まった流れが、まさにAPIの考え方なんです。裏側でどんな在庫管理システムが動いているかは客には見えませんが、レジという「窓口」を通じて、決まった形でやり取りができる。これがAPIです。

同じように、システムの世界でも、「顧客データをください」というお願いをAPIという窓口に投げると、裏側でデータベースにアクセスして、必要なデータを取ってきて、決まった形で返してくれる。こういう仕組みなんですね。

では、なぜAPIが必要なのか。もう少し深掘りしてみましょう。

1つ目の理由は、**安全性**です。もしAPIがなかったら、外部のシステムが直接データベースにアクセスすることになります。これは非常に危険です。間違った命令でデータを消してしまったり、悪意のある操作をされたりするリスクがあります。

APIを用意することで、「この操作だけは許可します」「この範囲のデータだけ見せます」という制御ができるんです。銀行のATMと似ています。ATMを通せば、預金を引き出したり残高を確認したりできますが、銀行のシステムに直接アクセスして他人の口座を操作することはできませんよね。APIも同じ役割を果たします。

2つ目の理由は、**再利用性**です。一度APIを作っておけば、Webサイトからも、スマホアプリからも、社内の別のシステムからも、同じAPIを使ってデータにアクセスできます。それぞれのシステムごとに別々の仕組みを作る必要がないんです。

例えば、顧客一覧を取得するAPIを1つ作っておけば、営業部のダッシュボード、カスタマーサポートの画面、経営陣のレポート、すべてが同じAPIを使える。これが再利用性です。

3つ目の理由は、**変更への強さ**です。例えば、データベースの構造を変更したとします。テーブル名を変えたり、カラムを追加したり。もしAPIがなければ、そのデータベースを使っているすべてのシステムを修正しなければなりません。

でも、APIがあれば、API自体の見た目(エンドポイントの形)はそのままで、裏側の処理だけを変えればいい。使う側のシステムは何も変更しなくていいんです。これが、システムを長く保守していく上で非常に重要なポイントなんです。

次に「REST」についてです。RESTは「REpresentational State Transfer」の略で、これはWebの設計ルールの一種です。ただ、この正式名称を覚える必要は全くありません。非エンジニアの方は「RESTって、APIを作るときの設計のお作法なんだな」くらいに思っていただければ十分です。

RESTという考え方が生まれたのは2000年のことです。当時、Web上でシステム同士がデータをやり取りする方法は、複雑で統一感がありませんでした。それぞれの会社、それぞれのシステムが、バラバラの方法でAPIを作っていたんです。

そこで、ロイ・フィールディングという研究者が、「Webの仕組みをうまく活用して、シンプルで分かりやすいAPI設計のルールを作ろう」と提案しました。それがRESTです。

RESTには色々と細かいルールがあるんですが、今日の講座では最も重要なポイントだけを押さえていきます。それは何かというと、**「URLの形を見れば、何をお願いしているか分かる」**という考え方です。

例えば、`/customers`というURLを見たら、「ああ、これは顧客に関するお願いだな」と分かる。`/orders`なら「注文に関することだな」と分かる。`/products`なら「商品についてだな」と分かる。

こういう風に、URLそのものが「意味を持つ」ように設計するのが、RESTの大きな特徴なんです。これを「リソース指向」と言います。リソースとは「資源」という意味ですが、ここでは「扱いたいデータのまとまり」と考えてください。

RESTが登場する前は、例えば`/getCustomerList`とか`/updateCustomerInfo`とか、動詞を含んだURLが多かったんです。でもRESTでは、URLには名詞(リソース名)だけを使って、動詞はHTTPメソッド(GET、POSTなど)で表現します。

この統一ルールのおかげで、初めて見るAPIでも「ああ、だいたいこういう構造だろうな」と予測できるようになりました。これがRESTの大きなメリットなんです。

まとめると、REST APIとは、**「Webの設計ルールに則った、システム同士が会話するための窓口」**ということです。そして非エンジニアの皆さんにとって重要なのは、「このAPI、何ができるの?」「どういうお願いができるの?」ということを理解できるようになることです。

コードを書く必要はありません。でも、「ああ、このAPIはこういう形でお願いできるんだな」というイメージを持てるようになると、エンジニアとの会話が格段にスムーズになります。

例えば、社内で新しいシステムを導入するとき、ベンダーから「このシステムはREST APIを提供しています」と言われたとします。そのとき、皆さんが「ああ、じゃあ他のシステムとの連携もしやすいですね」「どんなエンドポイントがありますか?」と質問できる。これが、非エンジニアにとってのAPIリテラシーなんです。

また、社内でシステム開発を企画するとき、「このシステムには外部連携用のREST APIを用意してほしい」と要件に入れることもできます。将来的な拡張性を考えた設計を、最初から求められるわけです。

このように、REST APIの基本を理解することは、非エンジニアの皆さんが、システム企画や運用に関わる上で、非常に重要なスキルになっているんです。

## 3-2. エンドポイントとリソースのイメージ(10分)

では、REST APIの具体的な形を見ていきましょう。ここで出てくるのが「エンドポイント」という言葉です。

エンドポイントとは、簡単に言うと**「APIにお願いするときのURL」**のことです。「この住所にお願いを届ける」というイメージですね。郵便を送るときの宛先住所と同じです。「〇〇県〇〇市〇〇町...」と住所を書けば、その家に届きますよね。エンドポイントも同じで、「このURLにアクセスすれば、この機能が使える」という目印なんです。

具体例を見てみましょう。画面に表示しているのは、顧客管理システムのAPI例です。

まず1つ目、`GET /customers`。これは「顧客の一覧をください」というお願いです。`GET`というのは、さっき学んだHTTPメソッドですね。「情報を見せてください」という意味でした。そして`/customers`が、お願いする先のエンドポイント、つまりURLのパス部分です。

完全なURLで書くと、`https://api.example.com/customers`のようになります。ただ、通常はドメイン部分は省略して、パスの部分だけで表記することが多いです。

このAPIを呼び出すと、システムに登録されているすべての顧客のデータが返ってきます。もちろん、何千人、何万人といる場合は、すべてを一度に返すわけにはいきませんので、通常はページング(ページ分け)という仕組みを使います。これについては後ほど説明しますね。

2つ目、`GET /customers/123`。これは「ID番号が123番の顧客の情報をください」というお願いです。`/customers`の後ろに`/123`と付いていますね。この`123`は顧客ID、つまり特定の一人を指定しています。

このような形を「パスパラメータ」と呼びます。URLのパスの一部として、対象を指定する方法です。`/customers/123`なら123番の顧客、`/customers/456`なら456番の顧客、という具合です。

第2回で学んだ「主キー」を覚えていますか? データベースのテーブルで、各行を一意に識別するためのIDでしたね。このパスパラメータに使われるIDは、まさにその主キーに対応しています。

3つ目、`POST /customers`。これは「新しい顧客を登録してください」というお願いです。`POST`は「新規登録」の意味でしたね。同じ`/customers`というエンドポイントでも、`GET`なら「見せて」、`POST`なら「登録して」と、メソッドによって意味が変わるんです。

これがRESTの面白いところです。エンドポイント自体は同じ`/customers`なのに、HTTPメソッドを変えるだけで、操作の意味が変わる。これによって、URLの数を減らせるんです。

もしメソッドの概念がなかったら、`/getCustomers`、`/createCustomer`、`/updateCustomer`、`/deleteCustomer`と、操作ごとに別々のURLを作る必要があります。でもRESTでは、`/customers`という1つのエンドポイントに対して、GETなら取得、POSTなら作成、PUTなら更新、DELETEなら削除、とメソッドで使い分けるんです。

これが「統一的なインターフェース」というRESTの原則の1つです。覚えやすくて、予測しやすい。これがRESTの利点なんですね。

ここで重要なのが「リソース」という考え方です。リソースとは日本語で「資源」という意味ですが、REST APIの世界では**「扱いたいデータのまとまり」**を指します。

例えば今の例で言うと、`/customers`の`customers`がリソース名です。これは「顧客」というデータのまとまりを表しています。同様に、`/orders`なら注文リソース、`/products`なら商品リソース、`/employees`なら社員リソース、という具合です。

RESTの考え方では、このリソースに対して、色々な操作をメソッドで指定するんですね。

- `GET`なら「見せて」
- `POST`なら「作って」
- `PUT`なら「更新して」
- `DELETE`なら「消して」

このように、**リソース名はそのままで、メソッドを変えることで操作を変える**。これがRESTの基本形です。

リソースという概念は、実は私たちの日常生活にも似たものがあります。例えば、図書館の本を考えてみてください。本というリソースに対して、「借りる」「返す」「予約する」「検索する」といった操作ができますよね。

REST APIも同じです。顧客というリソースに対して、「取得する」「作成する」「更新する」「削除する」という操作を定義するわけです。

では、ここで第2回と第3回の内容とつなげてみましょう。

第2回では、データベースの「テーブル」という概念を学びましたよね。顧客テーブル、注文テーブルといった形で、データを表で管理する考え方です。そして第3回では、そのテーブルに対してSQLという言語で命令を出す方法を学びました。

実は、REST APIのリソース名は、このテーブル名にほぼ対応するんです。

例えば、データベースに`customers`というテーブルがあったとします。このテーブルには、顧客のデータが行ごとに入っています。id、name、email、prefecture、といったカラムがあって、1行1行が1人の顧客を表しています。

そして、REST APIでは`/customers`というエンドポイントを作ります。すると、`GET /customers`で、このテーブルの中身をずらっと取ってくることができる。イメージとしては、第3回で学んだ`SELECT * FROM customers;`というSQLと同じような結果が返ってくるわけです。

つまり、**テーブルがリソースになり、エンドポイントになる**。この対応関係を理解しておくと、「ああ、このAPIは裏側でこのテーブルを触ってるんだな」というイメージが湧きやすくなります。

もう少し具体例を見てみましょう。

`GET /customers/123`というエンドポイントがあったとします。これは裏側で、どんな処理が行われているでしょうか。

答えは、`SELECT * FROM customers WHERE id = 123;`というようなSQLが動いているイメージです。特定のID、特定の1行だけを取ってくる操作ですね。APIのパスパラメータ`123`が、SQLのWHERE句の条件になっているわけです。

次に`POST /customers`。これは、新しい顧客を登録する操作でしたね。裏側では、`INSERT INTO customers (name, email, prefecture, ...) VALUES ('田中太郎', 'taro@example.com', '石川県', ...);`というようなSQLが実行されます。

APIを呼び出すときに、新しい顧客の情報(名前、メールアドレスなど)をリクエストボディに入れて送ります。それを受け取ったバックエンドが、SQLのINSERT文を組み立てて実行する、という流れです。

さらに`PUT /customers/123`という更新操作なら、裏側で`UPDATE customers SET name = '田中太郎', email = '...' WHERE id = 123;`といったSQLが動きます。

そして`DELETE /customers/123`という削除操作なら、`DELETE FROM customers WHERE id = 123;`というSQLになります。ただし、実務では本当にデータを消すのではなく、`UPDATE customers SET is_deleted = TRUE WHERE id = 123;`のように、削除フラグを立てるだけのことも多いです。これは第3回で学びましたね。

このように、REST APIとSQLは、言葉は違いますが、やっていることの本質は同じなんです。ただ、SQLは「データベースに直接命令する言葉」で、APIは「外部から安全にお願いするための窓口」という違いがあります。

ここで大事なポイントを整理しましょう。

まず、エンドポイントは**「どのリソース(データのまとまり)を扱うか」を示すURL**です。そして、HTTPメソッドは**「そのリソースに対してどんな操作をするか」を示す動詞**です。

この2つを組み合わせることで、「顧客リソースを取得する」「顧客リソースを作成する」「顧客リソースを更新する」といった操作を表現するわけです。

非エンジニアの皆さんがここで覚えておくべきことは、「エンドポイントを見れば、大体何の話をしているか分かる」ということです。

`/customers`なら顧客の話、`/orders`なら注文の話、`/products`なら商品の話。URL自体が意味を持つ。これがRESTの大きな利点なんですね。

また、エンドポイントの命名には、いくつかの慣習があります。

1つ目は、**リソース名は複数形にする**ことです。`/customer`ではなく`/customers`、`/order`ではなく`/orders`という具合です。これは「顧客の集まり」「注文の集まり」というニュアンスを表すためです。

2つ目は、**動詞を使わない**ことです。`/getCustomers`とか`/createOrder`ではなく、`/customers`、`/orders`という名詞だけにします。動詞はHTTPメソッドで表現するからです。

3つ目は、**階層構造を使う**ことです。例えば、「顧客IDが123の人の注文一覧」を取得したい場合、`/customers/123/orders`という形にします。「顧客123の下にある注文たち」という階層関係を、URLの構造で表現するわけです。

これらの慣習を知っておくと、他社のAPIドキュメントを読むときや、自社でAPI設計をするときに、とても役立ちます。

そして何より、エンジニアとの会話で「このエンドポイント、複数形にした方がいいんじゃないですか?」とか「この操作、別のメソッドで表現できませんか?」といった、一歩踏み込んだコミュニケーションができるようになります。

これが、非エンジニアがREST APIを理解する意義なんです。コードは書けなくても、設計の良し悪しを見極める目を持つことはできる。それが、これからのビジネスパーソンに求められるスキルなんですね。

## 3-3. 経営・業務視点でのAPI例(10分)

それでは、もう少し実務に近い例を見てみましょう。ここでは「顧客管理システム」を題材に、どんなAPIがあると便利なのか、業務視点で考えていきます。

まず、顧客管理システムで必要になりそうな操作を洗い出してみます。

- 顧客の一覧を見たい
- 特定の顧客の詳細情報を見たい
- 新しい顧客を登録したい
- 顧客の情報を更新したい(住所が変わった、電話番号が変わったなど)
- 顧客のステータスを変更したい(例:「見込み客」から「契約済み」へ)
- 顧客に対するメモを追加したい
- 顧客を検索したい(都道府県や業種で絞り込みたい)
- 顧客を削除したい(あるいは無効化したい)

こういった操作が考えられますよね。では、これらをREST API風に表現してみましょう。

**1. 顧客一覧の取得**

エンドポイント:`GET /customers`

これは、登録されている顧客全員の一覧を取得する操作です。営業担当者が「今日訪問する顧客リスト」を見たいとか、マーケティング部門が「全顧客のデータを分析したい」といった場合に使います。

実際には、何千人、何万人もいると大変なので、「1ページ20件」といったページング機能を付けることが多いです。その場合は、クエリパラメータを使います。

例:`GET /customers?page=1&limit=20`

これは「1ページ目を、1ページあたり20件で取得してください」という意味です。`page`がページ番号、`limit`が1ページあたりの件数です。

さらに、条件を絞り込むこともできます。

例:`GET /customers?prefecture=石川県&status=契約済み&page=1`

これは「石川県の、ステータスが契約済みの顧客を、1ページ目から20件取得する」という意味になります。

このように、クエリパラメータを使うことで、柔軟な検索ができるんです。これが、RESTful APIの便利なところです。

実務では、「どんな条件で絞り込みたいか」を事前に洗い出しておくことが重要です。都道府県? 業種? 契約日? 売上規模? こういった業務要件を整理して、「このパラメータが必要です」とエンジニアに伝えられるようになると、非常にスムーズです。

**2. 顧客詳細の取得**

エンドポイント:`GET /customers/{id}`

ここで`{id}`というのは、「顧客IDが入る」という意味です。実際には、`GET /customers/123`とか`GET /customers/456`という形になります。

これで、特定の一人の顧客について、名前、住所、電話番号、メールアドレス、会社名、担当者、契約日、購入履歴など、詳しい情報をすべて取得できます。

営業担当者が「この顧客、前回いつ訪問したっけ?」「どんな商品を買ってたっけ?」と確認したいときに使うAPIですね。

あるいは、カスタマーサポートが電話対応中に「お客様の情報を確認させてください」と言って、このAPIを叩いて詳細情報を表示する、という使い方もあります。

**3. 新規顧客の登録**

エンドポイント:`POST /customers`

新しい顧客をシステムに登録する操作です。この場合、名前や住所などの情報を、リクエストの中に含めてサーバーに送ります。

具体的には、JSON形式でデータを送ることが多いです。JSONについては次のセクションで詳しく学びますが、簡単に言うと「名前と値のペアで情報を表現する形式」です。

例えば、こんなデータを送ります。

```json
{
  "name": "田中太郎",
  "email": "taro.tanaka@example.com",
  "phone": "090-1234-5678",
  "prefecture": "石川県",
  "company": "株式会社サンプル"
}
```

これを`POST /customers`というエンドポイントに送ると、バックエンドが受け取って、データベースに新しい行を追加してくれます。

そして、登録が完了すると、「登録しました。新しい顧客のIDは123番です」という情報が返ってきます。この返ってきたIDを使って、さらに詳細情報を取得したり、更新したりできるわけです。

実務では、「必須項目は何か」「任意項目は何か」を明確にすることが大事です。例えば、名前とメールアドレスは必須だけど、電話番号は任意、といった具合です。これをAPI仕様書に明記しておくと、フロントエンドの開発者が「この項目は入力必須だな」と分かります。

**4. 顧客情報の更新**

エンドポイント:`PUT /customers/{id}`

既存の顧客情報を更新する操作です。例えば、ID=123の顧客の住所が変わったら、`PUT /customers/123`というエンドポイントに、新しい住所情報を含んだデータを送ります。

```json
{
  "address": "石川県金沢市◯◯町1-2-3",
  "phone": "090-9999-8888"
}
```

こんな形で、変更したい項目だけを送ることもできますし、すべての項目を送ることもあります。これは設計次第です。

ちなみに、`PUT`と似たメソッドに`PATCH`というものもあります。`PUT`は「全体を置き換える」イメージ、`PATCH`は「一部だけ変更する」イメージです。実務では、この使い分けはケースバイケースなので、チーム内で統一ルールを決めておくといいでしょう。

**5. 顧客ステータスの変更**

エンドポイント:`PUT /customers/{id}/status`

これは、ちょっと特殊な例です。顧客全体の情報を更新するのではなく、「ステータスだけ」を変更したい場合、専用のエンドポイントを用意することもあります。

例えば、営業プロセスで「見込み客」→「商談中」→「契約済み」→「休眠」といったステータスがあるとして、それを変更する専用のAPIを作るわけです。

```json
{
  "status": "契約済み"
}
```

こんなデータを`PUT /customers/123/status`に送ると、ID=123の顧客のステータスだけが「契約済み」に変わります。

なぜわざわざ専用のエンドポイントを作るかというと、ステータス変更という操作が頻繁に行われる場合、専用APIがあった方が使いやすいからです。また、ステータス変更のときだけ特別なログを残したい、通知を飛ばしたい、といった追加処理がある場合も、専用エンドポイントがあると実装しやすくなります。

**6. 顧客へのメモ追加**

エンドポイント:`POST /customers/{id}/notes`

これも、顧客情報の一部として「メモ」を追加する専用のAPIです。営業担当が「◯月◯日に電話した」「次回フォローは来週」「A商品に興味あり」といったメモを残せると便利ですよね。

```json
{
  "content": "2025年11月22日に電話。次回訪問は12月1日予定。",
  "author": "山田太郎"
}
```

こんなデータを`POST /customers/123/notes`に送ると、ID=123の顧客に新しいメモが追加されます。

このように、顧客というメインのリソースの下に、「ノート(メモ)」というサブリソースを配置する形になっています。`/customers/{id}/notes`というURL構造が、「顧客の下にあるメモたち」という階層関係を表しているわけです。

**7. 顧客の検索**

エンドポイント:`GET /customers/search?keyword=田中&prefecture=石川県`

あるいは、検索専用のエンドポイントを用意することもあります。顧客一覧の取得(`GET /customers`)とは別に、複雑な検索条件を扱いたい場合、こういう形もあり得ます。

例えば、フリーワード検索で「田中」と入力したら、名前、会社名、メモの中から「田中」を含むすべての顧客を返す、といった機能です。

**8. 顧客の削除(無効化)**

エンドポイント:`DELETE /customers/{id}`

顧客を削除する操作です。ただし、実務では本当にデータを消すのではなく、`is_deleted`というフラグを立てるだけのことが多いです。

あるいは、削除ではなく「無効化」という表現を使うこともあります。その場合、`PUT /customers/{id}/deactivate`のような専用エンドポイントを作ることもあります。

削除や無効化は、慎重に扱うべき操作なので、誤操作を防ぐために、確認画面を挟んだり、管理者権限を要求したり、といった仕組みを組み合わせることが多いです。

---

このように、REST APIでは、リソース(ここでは顧客)を中心に、様々な操作を表現できるんです。

ここで重要なのは、**「このAPIがあると、他のシステムとデータ連携しやすくなる」**ということです。

例えば、皆さんの会社でマーケティングオートメーション、いわゆるMAツールを使っているとします。HubSpot、Salesforce、Marketoといったツールですね。

このMAツールから、自社の顧客管理システムのデータを取得したい。そんなとき、`GET /customers`というAPIがあれば、MAツール側から定期的にデータを取りに来ることができます。1日1回、夜中に自動でデータを同期する、といった運用が可能になります。

あるいは、経営ダッシュボードを作って、リアルタイムで顧客数や売上を見たい。そんなときも、APIがあれば、ダッシュボード側から`GET /customers`や`GET /orders`を叩いて、最新のデータを取得できます。

さらに、スマホアプリを作って、営業担当が外出先から顧客情報を見られるようにしたい。これもAPIがあれば実現できます。Webブラウザからアクセスしても、スマホアプリからアクセスしても、同じAPIを使える。これが再利用性の高さです。

つまり、APIというのは、**システム同士をつなぐ「のり」**のようなものなんです。APIがしっかり設計されていると、後から新しいツールを導入したり、データを別の用途で使い回したりするのが、ずっと楽になります。

逆に、APIがないシステムは「閉じたシステム」になってしまいます。そのシステム専用の画面からしかデータにアクセスできない。他のツールと連携できない。これでは、ビジネスの変化に対応しづらくなります。

だからこそ、最近のシステム開発では「API ファースト」という考え方が主流になってきています。画面を作る前に、まずAPIを設計する。APIという土台がしっかりしていれば、その上にWebサイトを作ってもいいし、スマホアプリを作ってもいいし、他社のツールと連携してもいい。柔軟性が高まるわけです。

もう1つ、BI(ビジネスインテリジェンス)やレポート用途の例も見てみましょう。

例えば、「月次の売上レポート」を見たいとします。これも、REST API風に設計できます。

エンドポイント:`GET /reports/monthly-sales?year=2025&month=11`

こんな形で、年と月を指定すると、その月の売上データが返ってくる。これを、経営会議の資料作成に使ったり、ダッシュボードに表示したりできます。

あるいは、「今月新規登録した顧客の数」を知りたい場合、

エンドポイント:`GET /reports/new-customers?year=2025&month=11`

このように、レポート専用のエンドポイントを作ることもあります。

さらに、「商品別の売上ランキング」を見たい場合、

エンドポイント:`GET /reports/product-ranking?year=2025&month=11&limit=10`

こんな形で、上位10商品を取得する、といったこともできます。

このように、REST APIの考え方は、顧客や注文といった「モノ」を扱うだけでなく、レポートや集計といった「情報」を扱うこともできるんです。

実務では、「どんなレポートが定期的に必要か」を洗い出して、それをAPI化しておくと、自動化が進みます。毎月手作業でExcelに集計していた作業が、APIから自動でデータを取得してレポート生成、というように変わるわけです。

非エンジニアの皆さんにとって大事なのは、「自社の業務で、どんなAPIがあったら便利か?」を考えられるようになることです。

例えば、

- 「営業担当者が、スマホアプリから顧客情報を見られるようにしたい」
  → `GET /customers/{id}`のAPIが必要
- 「外部のコールセンターに、問い合わせ履歴を共有したい」
  → `GET /inquiries`のAPIが必要
- 「他部署のシステムから、在庫数をリアルタイムで確認したい」
  → `GET /products/{id}/stock`のAPIが必要
- 「会計システムと連携して、売上データを自動で取り込みたい」
  → `GET /orders?date_from=2025-11-01&date_to=2025-11-30`のAPIが必要

こんな風に、業務のニーズをAPI設計に落とし込む視点を持つことが、非エンジニアにとってのAPIリテラシーなんです。

そして、これを整理してエンジニアに伝えられるようになると、開発がスムーズに進みます。「こういう機能が欲しい」だけでなく、「こういうAPIがあれば実現できそう」というレベルで会話ができると、エンジニアも具体的なイメージを持ちやすくなります。

これが、非エンジニアがREST APIを学ぶ意義なんですね。システム開発の「共通言語」を持つことで、チーム全体の生産性が上がるんです。

## 3-4. AIに「API一覧」を作らせるデモ(10分)

それでは、ここからは実際にAIを使って、API設計を手伝ってもらうデモをお見せします。

今回の題材は、「問い合わせ管理システム」にしましょう。社内で顧客からの問い合わせを管理するシステムをイメージしてください。

まず、この問い合わせ管理システムには、こんな機能があるとします。

- 問い合わせの新規登録
- 問い合わせ一覧の取得(ステータスで絞り込めると便利)
- 問い合わせの詳細表示
- ステータスの変更(「未対応」→「対応中」→「完了」など)
- 担当者の割り当て
- メモの追加

これらの機能を、REST API風に設計したい。でも、「どんなエンドポイントにすればいいのか分からない」「HTTPメソッドはどれを使えばいいのか分からない」という状況です。

こんなとき、AIに頼むと便利です。では、実際にプロンプトを見てみましょう。

---

**プロンプト例:**

```
社内の「問い合わせ管理システム」のREST APIを設計したいです。

次のような機能があります:
- 問い合わせの新規登録
- 問い合わせ一覧の取得(ステータスで絞り込み)
- 問い合わせ詳細の表示
- ステータスの変更(対応中 → 完了など)
- 担当者の割り当て
- メモの追加

非エンジニアにもわかるように、
以下の項目を含めたAPI一覧を表形式で提案してください。

- HTTPメソッド
- パス(エンドポイント)
- 目的(日本語)
- 主な入力項目
- 主な出力項目
```

---

このプロンプトのポイントは、**「非エンジニアにもわかるように」**と明示していることです。こう書くことで、AIは専門用語を減らして、分かりやすい説明を心がけてくれます。

また、「表形式で提案してください」と指定することで、見やすい形で整理してくれます。箇条書きでバラバラに説明されるより、表になっている方が比較しやすいですよね。

では、このプロンプトをAIに投げると、AIが表形式でAPI一覧を提案してくれます。実際のAIの回答例を見てみましょう。

---

**AIの回答例:**

| No | HTTPメソッド | エンドポイント | 目的 | 主な入力項目 | 主な出力項目 |
|----|---------|--------------|------|------------|------------|
| 1 | POST | /inquiries | 新しい問い合わせを登録 | タイトル、内容、顧客名、メールアドレス、カテゴリー | 問い合わせID、登録日時 |
| 2 | GET | /inquiries | 問い合わせ一覧を取得 | ステータス(未対応/対応中/完了)、ページ番号 | 問い合わせID、タイトル、ステータス、登録日時、担当者名の配列 |
| 3 | GET | /inquiries/{id} | 特定の問い合わせの詳細を取得 | なし(URLのIDのみ) | 問い合わせの全情報(タイトル、内容、顧客情報、ステータス、メモ一覧など) |
| 4 | PUT | /inquiries/{id}/status | 問い合わせのステータスを変更 | 新しいステータス(未対応/対応中/完了) | 更新後のステータス、更新日時 |
| 5 | PUT | /inquiries/{id}/assign | 担当者を割り当て | 担当者ID | 担当者名、割り当て日時 |
| 6 | POST | /inquiries/{id}/notes | メモを追加 | メモの内容、記入者ID | メモID、記入日時 |

---

いかがでしょうか。このように、AIに業務内容と機能を伝えるだけで、REST API風の一覧表を作ってくれるんです。

では、この表を見ながら、ポイントを解説していきましょう。

**No.1の新規登録**

`POST /inquiries`となっています。`POST`なので「作成する」操作ですね。エンドポイントは`/inquiries`で、複数形になっています。これは「問い合わせというリソースの集まり」を表す慣習です。

主な入力項目として、タイトル、内容、顧客名などが挙げられています。これらは、問い合わせを登録するときに必要な情報ですね。Webの問い合わせフォームに入力する項目と対応しています。

そして主な出力項目として、問い合わせIDと登録日時が返ってきます。「登録しました、IDは123番です、登録日時は2025年11月22日14時30分です」という確認情報が返ってくるイメージです。

このIDは、後で詳細を見たり、ステータスを変更したりするときに使います。だから、必ず返す必要があるんですね。

**No.2の一覧取得**

`GET /inquiries`です。問い合わせの一覧を取得する操作ですね。

入力項目として「ステータス」「ページ番号」とあります。これは、`GET /inquiries?status=未対応&page=1`のような形で、クエリパラメータとして渡すイメージです。

「未対応の問い合わせだけを1ページ目から20件取得する」という使い方ができます。カスタマーサポートの担当者が、朝出社したら「今日対応すべき未対応の問い合わせ」を一覧で確認する、といった場面で使われます。

出力項目は、ID、タイトル、ステータスなど、一覧表示に必要な情報の配列が返ってきます。「配列」というのは、複数件のデータがリストで返ってくる形式のことです。次のセクションでJSONの形を見るときに、もっと具体的に分かると思います。

**No.3の詳細取得**

`GET /inquiries/{id}`です。特定の問い合わせの詳細を取得する操作ですね。

入力項目は「なし」となっていますが、正確には「URLに含まれるID」が入力です。例えば`GET /inquiries/123`なら、ID=123の問い合わせの詳細を取得します。

出力項目は、その問い合わせのすべての情報です。タイトル、内容、顧客情報、過去のやり取りのメモなど、詳細画面に必要なすべてのデータが返ってきます。

カスタマーサポートが電話対応中に「この問い合わせ、前回どんなやり取りしたっけ?」と確認するときに使うAPIです。

**No.4のステータス変更**

`PUT /inquiries/{id}/status`です。ここでは、問い合わせ全体の更新ではなく、「ステータスだけ」を変更する専用エンドポイントになっています。

こういう設計もあり得るんですね。もちろん、`PUT /inquiries/{id}`で問い合わせ全体を更新する形でもいいんですが、ステータス変更という操作が頻繁に行われるなら、専用エンドポイントを用意する方が分かりやすいこともあります。

また、ステータス変更のときだけ、「変更履歴を残す」「担当者に通知を送る」といった特別な処理を入れたい場合も、専用エンドポイントがあると実装しやすくなります。

入力項目は「新しいステータス」です。例えば`{"status": "完了"}`というデータを送ると、そ問い合わせのステータスが「完了」に変わります。

**No.5の担当者割り当て**

`PUT /inquiries/{id}/assign`です。これも専用エンドポイントの例ですね。「この問い合わせを、誰々さんに割り当てる」という操作を、1つのAPIとして表現しています。

例えば、管理者が「この問い合わせは田中さんに対応してもらおう」と判断して、担当者IDを指定します。すると、その問い合わせの担当者が田中さんに設定され、田中さんにメール通知が飛ぶ、といった仕組みです。

入力項目は「担当者ID」、出力項目は「担当者名と割り当て日時」となっています。これで、「誰が、いつ担当者になったか」が記録されるわけです。

**No.6のメモ追加**

`POST /inquiries/{id}/notes`です。特定の問い合わせに対して、メモを追加する操作です。`POST`なので「新しいものを作る」という意味ですね。メモというリソースを、問い合わせの下に追加する、というイメージです。

`/inquiries/{id}/notes`というURL構造が、「問い合わせの下にあるメモたち」という階層関係を表しています。これがRESTの「階層構造」の考え方です。

担当者が「お客様に電話で確認した内容」「次回のフォローアップ予定」といったメモを残せると、チーム内で情報共有しやすくなりますよね。

入力項目は「メモの内容」と「記入者ID」です。誰が書いたメモなのかを記録することで、後から「このメモ、誰が書いたんだっけ?」と確認できます。

---

さて、このようにAIに作ってもらったAPI一覧を見て、皆さんは何をすればいいのか。

まず、「この一覧、うちの業務に合ってるかな?」とチェックします。

例えば、「問い合わせの削除」の機能が抜けてるかもしれません。あるいは、「カテゴリーごとに集計したい」という要望があるなら、`GET /inquiries/summary?category=商品`みたいなAPIが追加で必要かもしれません。

足りないものがあれば、AIに「こういう機能も欲しいんですが、エンドポイントを追加してください」とお願いすればいいんです。

例えば、

```
この一覧に、以下の機能も追加したいです。
- 問い合わせの削除(論理削除)
- カテゴリー別の集計(各カテゴリーの件数を取得)
- 担当者別の問い合わせ一覧(特定の担当者が抱えている問い合わせを取得)

これらのエンドポイントも提案してください。
```

こんな風にAIに追加で依頼すれば、さらに表が充実します。

そして、この一覧を、エンジニアとの打ち合わせの材料にします。「このAPI一覧で、うちの業務はカバーできますか?」「ステータスの変更は専用エンドポイントがいいですか、それとも全体の更新でまとめた方がいいですか?」といった会話ができるようになります。

これが、非エンジニアのAPI設計への関わり方です。コードは書けなくても、**「どんな機能が必要で、どんな形で提供されるべきか」を整理する**ことはできるんです。

そして、こういう整理をAIに手伝ってもらうことで、作業時間を大幅に短縮できます。昔なら、エンジニアと何度も打ち合わせして、ホワイトボードに書いて、Excel方眼紙に表を作って…という作業が必要でしたが、今はAIに最初の叩き台を作ってもらって、それをブラッシュアップする形で進められます。

AIは「完璧な答え」を出してくれるわけではありません。でも、「80点の叩き台」を一瞬で作ってくれます。それを、皆さんの業務知識で「95点」に仕上げる。これが、これからの仕事の進め方なんです。

最後に、このAPI一覧を使って、さらにAIに質問することもできます。

例えば、

```
この「問い合わせ一覧取得」のAPI、
ステータスが「未対応」のものだけを取得したい場合、
具体的にどんなURLになりますか?
```

とか、

```
「メモ追加」のAPIで送るデータは、
どんな形式(JSON)で送ればいいですか?
サンプルを見せてください。
```

といった質問をAIにすることで、より具体的な理解が深まります。

あるいは、

```
このAPI設計で、セキュリティ上注意すべき点はありますか?
```

と聞けば、AIが「担当者の権限チェックが必要です」「メモの記入者IDは、ログインユーザーのIDと一致するか確認すべきです」といったアドバイスをくれるかもしれません。

こんな風に、AIは「設計のたたき台を作る相棒」として、非常に強力なツールになるんです。

そして重要なのは、**AIが作ったものを鵜呑みにしないこと**です。AIは業務の細かい事情までは知りません。「うちの会社では、問い合わせの担当者は複数人アサインできるようにしたい」とか「カテゴリーは3階層の構造になってる」とか、そういう独自ルールは、皆さんが補足する必要があります。

AIが作った叩き台を見て、「ここは違うな」「これが足りないな」と気づけること。そして、それをAIにフィードバックして修正してもらうこと。これが、AIディレクターとしてのスキルなんです。

では、このセクションのまとめをしましょう。

REST APIの基本は、**リソース(データのまとまり)を中心に、HTTPメソッドで操作を表現する**ことです。エンドポイントを見れば、大体何の話をしているか分かる。これがRESTの利点です。

そして、業務視点でAPIを考えるときは、「どんな操作が必要か」を洗い出すことから始めます。一覧取得、詳細取得、新規登録、更新、削除、ステータス変更、メモ追加…などなど。

これらをAIに整理してもらい、エンジニアと相談しながらブラッシュアップする。このスタイルが、これからの非エンジニアの働き方なんです。

第5回、第6回では、今日考えたこのAPI設計をもとに、実際にデータベース設計をして、ミニCRUDアプリの形を作っていきます。今日学んだREST APIの知識が、データベースとどうつながるのか、実際に手を動かしながら体験していただきます。楽しみにしていてください。

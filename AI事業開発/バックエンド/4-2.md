## 2. HTTPとは? – Webの「会話のルール」を知る ナレーション原稿

---

それでは、第2章「HTTPとは? – Webの「会話のルール」を知る」に入っていきましょう。

このパートでは、私たちが普段何気なく使っているWebブラウザやアプリの裏側で、実際にどんなやりとりが行われているのか、その「会話のルール」を理解していきます。

HTTPという言葉、皆さんも聞いたことがあるかもしれません。URLの最初に「http://」とか「https://」って書いてありますよね。でも、「HTTPって結局なんなの?」と聞かれると、ちょっと説明に困ってしまう…そんな方も多いのではないでしょうか。

今日のこのパートを終える頃には、HTTPの基本的な仕組みを自分の言葉で説明できるようになります。そして、エンジニアの方と会話するときに「あ、この人HTTPの基本がわかってるな」と思ってもらえるレベルまで、一緒に到達していきましょう。

では、まず最初のテーマです。

### 2-1. Webアクセスで何が起きている? – URLの分解

皆さん、普段インターネットで何かを検索したり、サイトを見たりするとき、ブラウザのアドレスバーにURLが表示されていますよね。このURL、実は私たちが「どこに、何をお願いしに行くか」を示す住所のようなものなんです。

画面に表示されているこちらのURLを見てください。

```
https://example.com/customers?pref=ishikawa
```

一見すると英数字の羅列で、ちょっと難しそうに見えるかもしれません。でも、これをパーツごとに分解して見ていくと、実はとてもシンプルな構造になっています。

まず、一番最初の部分、`https://` の部分です。

これは**プロトコル**と呼ばれるもので、「通信の方法」を表しています。HTTPSのSは「Secure(安全)」のSで、暗号化された安全な通信ですよ、という印です。私たちがクレジットカード番号や個人情報を入力するようなサイトでは、必ずこの「https」になっているはずです。

最近では、ほとんどのサイトがHTTPSに対応していますが、まれに「http」だけのサイトもあります。そういうサイトでは、個人情報の入力は避けた方が安全です。

次に、`example.com` の部分です。

これは**ドメイン**と呼ばれていて、いわば「建物の住所」のようなものです。インターネット上のどのコンピュータ(サーバー)に行けばいいのかを示しています。

例えば、皆さんがよく使うサイト、「amazon.co.jp」とか「rakuten.co.jp」とか、これらがすべてドメインです。このドメインを見れば、「あ、今Amazonにアクセスしているんだな」とか「楽天のサイトだな」というのがわかるわけですね。

そして、その次の部分、`/customers` です。

これは**パス**と呼ばれます。建物に例えるなら、「建物の中のどの部屋に行くか」を表しています。

例えば、ECサイトなら `/products` で商品一覧のページ、`/cart` でカートのページ、`/mypage` でマイページ、というように、サイトの中の「どこ」にアクセスするかをこのパスで指定しているんです。

最後に、`?pref=ishikawa` の部分です。

これは**クエリパラメータ**と呼ばれるもので、「条件」や「絞り込み」を表しています。

この例で言うと、「pref(都道府県)がishikawa(石川県)のデータをください」という条件を伝えているわけです。

ECサイトで商品を検索するとき、価格帯で絞り込んだり、カラーで絞り込んだりしますよね。あのときURLを見ると、`?price=1000-5000` とか `?color=red` みたいな文字列が追加されているはずです。これがクエリパラメータです。

さて、このようにURLを分解してみると、それぞれのパーツが「どこに」「何を」お願いしに行くかを表していることがわかりますね。

もう一度、建物の例えで整理してみましょう。

- **プロトコル(https://)** = 「どんな交通手段で行くか」(安全な方法で行きます)
- **ドメイン(example.com)** = 「どの建物に行くか」(建物の住所)
- **パス(/customers)** = 「建物の中のどの部屋に行くか」(顧客情報の部屋)
- **クエリパラメータ(?pref=ishikawa)** = 「どんなお願いをするか」(石川県の人だけ教えてください)

このように考えると、なんだか親しみやすくなってきませんか?

ちなみに、AIを活用する場面でも、このURL構造の理解は役立ちます。

例えば、こんなプロンプトをAIに投げてみましょう。

「このURLを分解して、それぞれが何を意味しているか、非エンジニアにもわかるように説明してください。URL: https://example.com/customers?pref=ishikawa」

このようにAIに聞けば、URLの構造をもっと詳しく解説してくれます。また、実務で「このURLってどういう意味だろう?」と思ったときに、AIに投げて確認する、という使い方もできますね。

では、次のテーマに進みましょう。

### 2-2. HTTPメソッド – GETとPOSTの違いをざっくり

さて、URLで「どこに行くか」はわかりました。では、そこで「何をお願いするか」はどうやって伝えるのでしょうか?

ここで登場するのが**HTTPメソッド**です。

メソッドというのは、「お願いの種類」だと考えてください。同じ場所(URL)に行くとしても、「見せてください」というお願いなのか、「新しく登録してください」というお願いなのか、お願いの内容によって使い分けるんです。

代表的なHTTPメソッドには、いくつか種類がありますが、非エンジニアの皆さんがまず押さえておきたいのは、この2つです。

**GET(ゲット)**と**POST(ポスト)**です。

まず、**GET**から見ていきましょう。

GETは、「情報を見せてください」「取得してください」というお願いです。

例えば、ECサイトで商品一覧を見るとき、これはGETです。サーバーに対して「商品のデータを見せてください」とお願いしているわけですね。

顧客管理システムで顧客リストを表示するとき、これもGETです。「顧客データを取得してください」というお願いです。

GETの特徴は、**データを取ってくるだけで、サーバー側のデータは変更しない**ということです。何度GETしても、データベースの中身は変わりません。ただ「見る」だけです。

次に、**POST**です。

POSTは、「新しい情報を登録してください」というお願いです。

例えば、ECサイトで新規会員登録をするとき、これはPOSTです。名前やメールアドレス、パスワードなどの情報を送って、「この新しい会員を登録してください」とお願いしているわけです。

お問い合わせフォームで問い合わせ内容を送信するとき、これもPOSTです。サーバーに新しいデータを追加してもらう、というイメージですね。

POSTの特徴は、**サーバー側のデータを変更する(追加する)**ということです。POSTを実行すると、データベースに新しいレコードが追加されます。

さて、GETとPOSTの違い、なんとなくイメージできましたか?

簡単にまとめると、こうなります。

- **GET** = 「見せてください」(データを取得するだけ)
- **POST** = 「登録してください」(新しいデータを追加する)

実は、HTTPメソッドには他にも種類があります。簡単に名前だけご紹介しておきますね。

- **PUT**(プット) = 既存のデータを更新してください
- **DELETE**(デリート) = データを削除してください

これらも、お願いの種類によって使い分けられています。

例えば、顧客情報の住所を変更するなら**PUT**、退会処理をするなら**DELETE**、というイメージです。

ただ、今日の段階では、GETとPOSTの2つだけしっかり理解できていればOKです。PUTとDELETEは、また実務で出てきたときに「あ、更新と削除のメソッドだな」と思い出せれば十分です。

では、ここで具体的なシーンで考えてみましょう。

ECサイトを例にします。

- **商品一覧ページを表示する** → これは**GET**です。商品データを取得して見せているだけで、データベースは何も変わりません。
  
- **商品の詳細ページを見る** → これも**GET**です。特定の商品のデータを取ってきて表示しているだけです。

- **新規会員登録をする** → これは**POST**です。名前、メールアドレス、パスワードなどの情報を送って、新しい会員データを登録してもらいます。

- **カートに商品を追加する** → これも実は**POST**です。カートという「一時的な注文リスト」に、新しい商品を追加しているからです。

このように、同じECサイトの中でも、やりたいことによってメソッドが変わるんですね。

ここで大事なのは、**皆さんがエンジニアと会話するときに、このメソッドの違いを意識できているかどうか**です。

例えば、システム開発の打ち合わせで、「顧客一覧を表示する機能が欲しい」と言うとき、エンジニアの頭の中では「これはGETだな」と理解されます。

逆に、「新しい顧客を登録できるようにしたい」と言えば、「POSTが必要だな」と考えるわけです。

メソッドの名前を正確に言う必要はありませんが、「見るだけなのか」「データを変更するのか」を意識して伝えられると、エンジニアとのコミュニケーションがぐっとスムーズになります。

そして、これはAIとの対話でも同じです。

例えば、「顧客一覧を取得するAPIを設計してください」とAIにお願いすれば、AIは自動的に「これはGETメソッドだな」と判断してAPI設計を提案してくれます。

逆に、「新しい顧客を登録するAPIを設計してください」と言えば、POSTメソッドのAPIを提案してくれるでしょう。

このように、HTTPメソッドの基本を理解しておくだけで、開発者との会話もAIとの対話も、格段にスムーズになるんです。

### 2-3. ステータスコード – 200 / 404 / 500を理解する

さて、私たちがURLを指定して、メソッド(GETやPOST)でお願いを出しました。すると、サーバーから何らかの「返事」が返ってきます。

この返事の中には、「お願いがうまくいったかどうか」を示す番号が含まれています。これを**ステータスコード**と呼びます。

ステータスコードは3桁の数字で表されていて、数百種類あるんですが、非エンジニアの皆さんが知っておくべきは、たった3つです。

**200**、**404**、そして**500**です。

この3つさえ押さえておけば、実務で困ることはほとんどありません。では、1つずつ見ていきましょう。

まず、**200番**です。

これは「**OK**」という意味です。「あなたのお願い、ちゃんと受け付けましたよ。成功しました」という返事です。

例えば、商品一覧ページを開いたとき、画面にちゃんと商品が表示されていれば、裏側では200が返ってきています。

顧客データを取得するAPIを叩いて、データがちゃんと返ってきたら、これも200です。

つまり、**200 = すべて順調、問題なし**と覚えておいてください。

開発中やテスト中に「ちゃんと動いてるかな?」と確認するとき、エンジニアは「200が返ってきてるか?」をチェックします。200が返っていれば、「よし、うまくいってる」と安心できるわけです。

次に、**404番**です。

これは「**Not Found**」、つまり「見つかりませんでした」という意味です。

皆さんも、ブラウザで何かを開こうとしたときに「404 Not Found」という画面を見たことがあるかもしれません。あれです。

これは、指定されたURL(パス)に対応するページやデータが存在しない、ということを示しています。

例えば、`https://example.com/customers/999` というURLにアクセスしたとします。でも、ID=999の顧客データが存在しなかったら、サーバーは404を返します。「そのIDの顧客は見つかりませんでしたよ」という返事です。

あるいは、システム開発中に新しいページを作ったのに、URLの設定を間違えていたり、デプロイ(本番環境への反映)がうまくいっていなかったりすると、404が出ます。

ですので、**404 = 指定されたものが見つからない**と覚えておいてください。

404が出たときの対処法としては、

- URLが間違っていないか確認する
- そもそもそのページやデータが存在しているか確認する
- デプロイやファイルの配置がちゃんとできているか確認する

といったことをチェックします。

最後に、**500番**です。

これは「**Internal Server Error**」、日本語にすると「サーバー内部エラー」です。

これは、**サーバー側で何か問題が起きました**という返事です。

例えば、データベースとの接続が切れてしまったとか、プログラムにバグがあってエラーが発生したとか、サーバー側の処理で予期しない問題が起きたときに500が返ってきます。

つまり、**500 = サーバー側のトラブル**です。

200や404は、ある意味「想定内」の返事なんですが、500は「想定外のトラブルが起きた」というサインです。

ですので、500エラーが出たら、開発者やシステム管理者がすぐに調査に動く必要があります。

実務でよくあるのは、システムの運用監視をしているときに「500エラーが多発しています」という報告が上がってくるケースです。こうなると、バックエンド側のログを確認して、何が原因で500が出ているのかを突き止める必要があります。

例えば、

- データベースのテーブルが存在しない
- SQLの文法が間違っている
- 外部APIとの連携でタイムアウトが発生している
- サーバーのメモリやディスク容量が足りなくなっている

といった原因が考えられます。

非エンジニアの皆さんがこの原因を直接解決する必要はありませんが、「500が出た = サーバー側の問題だから、開発チームに報告しなきゃ」ということがわかるだけで、対応がとてもスムーズになります。

そして、ここでもAIが役立ちます。

例えば、エラーログに「500 Internal Server Error」と出ていたとします。そのエラーメッセージをそのままAIに貼り付けて、こう聞いてみましょう。

「バックエンドのエラーログに『500 Internal Server Error』が出ているのですが、非エンジニアでもイメージできるように、どんなトラブルの可能性があるか教えてください」

すると、AIは考えられる原因をいくつか挙げてくれます。データベース接続エラーかもしれない、プログラムのバグかもしれない、外部サービスとの連携が失敗しているかもしれない、といった具合です。

その情報を持って開発チームに相談すれば、「あ、この人ちゃんと理解してるな」と思ってもらえますし、調査もスムーズに進みます。

さて、ステータスコードのまとめです。

- **200** = OK、成功しました
- **404** = Not Found、見つかりませんでした
- **500** = Server Error、サーバー側で問題が起きました

この3つさえ覚えておけば、実務でのトラブル対応や、エンジニアとのコミュニケーションで困ることはありません。

### まとめ

さて、第2章「HTTPとは? – Webの「会話のルール」を知る」、いかがでしたか?

今日学んだことを、もう一度振り返ってみましょう。

まず、**URLの構造**です。

- **プロトコル(https://)** = 通信の方法
- **ドメイン(example.com)** = サイトの住所
- **パス(/customers)** = サイトの中のどの部屋か
- **クエリパラメータ(?pref=ishikawa)** = 条件や絞り込み

次に、**HTTPメソッド**です。

- **GET** = 情報を見せてください(データを取得するだけ)
- **POST** = 新しい情報を登録してください(データを追加する)

そして、**ステータスコード**です。

- **200** = 成功
- **404** = 見つからない
- **500** = サーバー側のトラブル

これらの基本を理解しておくだけで、Webの裏側で何が起きているのか、そのイメージがぐっと鮮明になります。

そして、エンジニアとの会話で「この人、HTTPの基本がわかってるな」と思ってもらえるレベルになりましたし、AIに対しても的確な質問ができるようになりました。

さあ、次の章では、いよいよ「REST API」という仕組みに踏み込んでいきます。

今日学んだHTTPの知識を土台にして、APIがどんな形をしているのか、どうやって設計するのか、一緒に学んでいきましょう。

それでは、第3章でお会いしましょう!

# 第4回「5. バックエンドがしていることを4ステップで言語化する」ナレーション原稿

## 5-1. 4ステップモデルの提示(7分)

それでは、ここまで学んできたHTTP、REST API、そしてJSONの知識を総動員して、バックエンドが実際に何をしているのかを、誰にでもわかる形で言語化していきましょう。

皆さん、ここまでの内容を振り返ってみてください。第1回では、フロントエンドとバックエンドの役割分担について学びました。第2回では、データベースのテーブル構造について理解を深めました。そして第3回では、SQLというデータベースへの命令文を体験しましたね。

今日は、HTTPやREST API、JSONについて学んできました。これらすべてが、実は密接につながっているんです。

では、画面を見てください。バックエンドがしていることを、この4つのステップで整理できます。

**ステップ1:リクエストを受け取る**
**ステップ2:内容を理解し、ビジネスルールを適用する**
**ステップ3:データベースを操作する**
**ステップ4:結果をJSONにまとめて返す**

この4ステップです。シンプルですよね。でも、この4つのステップを理解しているだけで、エンジニアとの会話が驚くほどスムーズになります。

それぞれを詳しく見ていきましょう。

**ステップ1:リクエストを受け取る**

これは今日の前半で学んだHTTPの世界です。フロントエンド、つまり画面側から「こういう情報が欲しい」「こういうデータを登録したい」というお願いが届きます。このお願いには、URLがあって、HTTPメソッドがあって、場合によってはJSONデータが添付されています。

例えば「GET /customers?pref=ishikawa」というリクエストなら、「石川県の顧客一覧をください」というお願いが届いたわけです。POSTメソッドで「/customers」にJSONデータが送られてきたら、「新しい顧客を登録してください」というお願いですね。

バックエンドは、まずこのリクエストを正確に受け取ります。これが第1ステップです。

**ステップ2:内容を理解し、ビジネスルールを適用する**

次に、受け取ったリクエストの内容を理解して、「このお願いに対して、どう処理すべきか」を判断します。ここが、実は非常に重要なポイントなんです。

第1回で、バックエンドの役割として「ビジネスロジック」という言葉が出てきたのを覚えていますか?これがまさに、このステップ2で行われていることなんです。

例えば、顧客を新規登録するリクエストが来たとします。バックエンドは単純にデータベースに保存するだけではありません。「このメールアドレスは既に登録されていないか?」「入力された電話番号の形式は正しいか?」「都道府県名は正しいリストの中にあるか?」こういったチェックをします。

あるいは、「石川県の顧客一覧」を取得するリクエストの場合、「このユーザーには石川県のデータを見る権限があるか?」といった権限チェックもこのステップで行われることがあります。

つまり、ステップ2では、「何をすべきか」「どう処理すべきか」という判断と準備をしているんです。

**ステップ3:データベースを操作する**

さあ、ここで第3回で学んだSQLの世界が登場します。ステップ2で判断した内容に基づいて、実際にデータベースに対してSQLを実行します。

顧客一覧を取得するなら「SELECT」文、新規登録なら「INSERT」文、更新なら「UPDATE」文、削除なら「DELETE」文ですね。

例えば「石川県の顧客一覧」なら、「SELECT * FROM customers WHERE prefecture = '石川県';」というようなSQLを実行して、該当するレコードを取得します。

データベースから結果が返ってきます。これを一旦、バックエンド側で受け取ります。

**ステップ4:結果をJSONにまとめて返す**

最後のステップです。データベースから取得した結果を、フロントエンドが理解できる形、つまりJSONに整形して返します。

今日学んだJSONの形式を思い出してください。データベースのテーブルの行と列は、JSONの配列とオブジェクトに変換されます。そして、HTTPのステータスコードも一緒に返します。成功なら200、見つからなければ404、エラーなら500、という具合にです。

こうして、フロントエンド側にレスポンスが届き、画面に結果が表示される、という流れになります。

---

さて、この4ステップを改めて見てみましょう。

**リクエストを受け取る→内容を理解し、ビジネスルールを適用する→データベースを操作する→結果をJSONにまとめて返す**

実は、これまでの3回の講座で学んできた内容が、すべてこの4ステップのどこかに対応しているんです。

ステップ1と4は、今日学んだHTTP・REST API・JSONの世界です。
ステップ3は、第3回で学んだSQLの世界です。
ステップ2は、第1回で触れたビジネスロジックの世界です。

つまり、皆さんは既に、バックエンドがしていることの全体像を理解するための基礎知識を持っているんです。

非エンジニアの皆さんが、この4ステップで説明できるようになると、何が変わるでしょうか?

例えば、社内のエンジニアに「この機能、今どこまでできていますか?」と聞くときに、「リクエストは受け取れていますか?」「ビジネスルールのチェックは実装済みですか?」「データベースへの書き込みは確認できましたか?」といった、具体的な質問ができるようになります。

あるいは、外部のシステム開発会社に見積もりを依頼するときに、「このAPIは、ステップ2のビジネスルール部分が複雑なので、工数が多くなりそうですね」といった会話ができるようになります。

これは、非常に大きな変化です。「何となく難しそう」「よくわからないけどお願いします」という状態から、「4つのステップのどこで何が起きているか」を理解している状態になるわけですから。

## 5-2. 具体例で4ステップをなぞる(5分)

では、実際の例で、この4ステップを追いかけてみましょう。

例として、「石川県の顧客一覧を取得する」というリクエストを考えます。APIのエンドポイントは「GET /customers?pref=ishikawa」です。

**ステップ1:リクエストを受け取る**

まず、フロントエンド側、つまりブラウザやアプリから、このリクエストが届きます。

HTTPメソッドは「GET」です。パスは「/customers」です。そして、クエリパラメータとして「pref=ishikawa」が付いています。

バックエンドは、「ああ、顧客リソースに対するGETリクエストだな。しかも、prefというパラメータで石川県を指定しているな」と理解します。

**ステップ2:内容を理解し、ビジネスルールを適用する**

次に、バックエンドは受け取った内容を精査します。

「pref=ishikawa」というパラメータは有効か?文字列として正しく受け取れているか?都道府県名として認識できる値か?

また、このリクエストを送ってきたユーザーは、顧客データを閲覧する権限を持っているか?場合によっては、ログインしているユーザーのIDをチェックして、権限を確認します。

すべて問題なければ、「では、データベースに対して石川県の顧客を取得するクエリを実行しよう」と判断します。

もし何か問題があれば、ここでエラーを返します。例えば、権限がなければ403エラー、パラメータの形式が間違っていれば400エラーといった具合です。

**ステップ3:データベースを操作する**

さあ、ここで第3回で学んだSQLの出番です。

バックエンドは、次のようなSQLを組み立てて実行します。

「SELECT * FROM customers WHERE prefecture = '石川県';」

データベースはこのクエリを受け取り、customersテーブルの中から、prefecture列が「石川県」になっているレコードをすべて取り出して返します。

例えば、5件のレコードが該当したとしましょう。データベースからは、5行分のデータが返ってきます。

**ステップ4:結果をJSONにまとめて返す**

最後に、バックエンドは、データベースから受け取った5件のレコードを、JSON形式に変換します。

今日学んだように、複数のレコードは配列になります。各レコードはオブジェクトです。

```json
[
  {
    "id": 1,
    "name": "田中太郎",
    "email": "taro.tanaka@example.com",
    "prefecture": "石川県"
  },
  {
    "id": 2,
    "name": "山田花子",
    "email": "hanako.yamada@example.com",
    "prefecture": "石川県"
  }
  // ... 以下3件
]
```

こういった形のJSONを作り、HTTPステータスコード200(成功)と一緒にフロントエンドに返します。

フロントエンドは、このJSONを受け取って、画面に一覧表示する、という流れになります。

---

いかがでしょうか。4つのステップを順番に追っていくと、「バックエンドがしていること」が、かなり具体的にイメージできるのではないでしょうか。

この流れを図で表すと、左から右に、フロント→バックエンド→データベース、そしてまた逆にデータベース→バックエンド→フロントと戻ってくるイメージです。

バックエンドは、その真ん中で、リクエストを受け取って、判断して、データベースとやり取りして、結果を整形して返す。この4ステップを繰り返しているんです。

## 5-3. AIに「処理の言語化」をさせるプロンプト例(3分)

最後に、この4ステップの理解を、AIを使ってさらに深める方法をご紹介します。

実は、APIの仕様だけを見ても、「裏側で何が起きているか」は想像しにくいことがあります。特に、複雑なビジネスルールが絡む場合は、エンジニアに直接聞かないとわからないこともあります。

そんなとき、AIに「このAPIは裏側で何をしているのか、4ステップで説明して」とお願いすると、非常にわかりやすい説明を得られることがあります。

画面に表示しているのが、実際のプロンプト例です。

---

**プロンプト例**

```
次のAPIが裏側で行っている処理を、
非エンジニアにもわかるように4ステップで説明してください。

API:
GET /customers?pref=ishikawa
```

---

このようにAIに聞くと、AIは次のような回答を返してくれるでしょう。

「ステップ1では、GETメソッドで/customersへのリクエストを受け取り、クエリパラメータpref=ishikawaを解析します。ステップ2では、prefパラメータが有効な都道府県名かをチェックし、リクエストユーザーの権限を確認します。ステップ3では、データベースに対してSELECT文を実行し、石川県の顧客レコードを取得します。ステップ4では、取得した結果をJSON形式に変換し、ステータスコード200と共にフロントエンドに返します。」

といった具合です。

このように、AIに処理の流れを言語化してもらうことで、「このAPIは何をしているのか」を、コードを読まなくても理解できるようになります。

さらに、この説明を社内のドキュメントとして保存しておけば、将来、別の人がこのシステムを引き継ぐときにも役立ちます。エンジニアでない人が読んでも理解できる資料になるわけです。

皆さんも、ぜひこのプロンプトを使って、実際に手を動かしてみてください。自社のシステムや、これから作りたいシステムのAPIについて、AIに4ステップで説明してもらう。そうすると、「バックエンドがしていること」が、より具体的にイメージできるようになります。

---

それでは、この「バックエンドがしていることを4ステップで言語化する」セクションをまとめましょう。

今日学んだ4ステップ、もう一度確認します。

**ステップ1:リクエストを受け取る**
**ステップ2:内容を理解し、ビジネスルールを適用する**
**ステップ3:データベースを操作する**
**ステップ4:結果をJSONにまとめて返す**

この4つです。

この4ステップを理解していれば、バックエンドが「どこで」「何を」しているのかが明確になります。

第1回のフロントとバックの役割分担、第2回のテーブル構造、第3回のSQL、そして今日のHTTP・REST・JSONが、すべてこの4ステップの中に組み込まれているんです。

ですから、非エンジニアの皆さんでも、この4ステップで説明できるようになれば、エンジニアとの会話は驚くほどスムーズになります。「このAPIのステップ2の部分、もう少し詳しく教えてください」とか、「ステップ3のSQL、パフォーマンスは大丈夫ですか?」といった質問ができるようになるわけです。

そして、AIを活用すれば、複雑なAPIの処理内容も、わかりやすく言語化してもらえます。

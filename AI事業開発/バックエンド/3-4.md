### 4-1. INSERT:新しい行を追加する(10分)

それでは、ここからは「データを書き込む」側の話に進んでいきましょう。

さきほどまでは、`SELECT`を使って「読む」体験をしてきました。欲しい条件でデータを取り出す、並び替える、絞り込む。これらはすべて「既にあるデータを見る」という操作でしたね。

でも、実際のシステムでは、「新しいお客さまが登録する」「新しい注文が入る」「新しい問い合わせが届く」といったことが日々起きています。こういった「新しいデータをテーブルに追加する」ときに使うのが、`INSERT`という命令です。

INSERTは、英語で「挿入する」という意味ですね。データベースのテーブルに、新しい行を1つ追加する。そういうイメージを持っていただければ大丈夫です。

画面に表示しているのが、INSERTの基本的な書き方です。

```sql
INSERT INTO customers (name, email, prefecture)
VALUES ('山田太郎', 'taro@example.com', '東京都');
```

少し分解して見ていきましょう。

まず、`INSERT INTO customers`。これは「customersというテーブルに挿入してください」という意味です。INTOは「〜の中へ」という英語ですから、「customersの中に入れる」というニュアンスですね。

次に、カッコの中に`name, email, prefecture`と並んでいます。これは「どのカラムに値を入れるか」を指定している部分です。つまり、「名前、メールアドレス、都道府県の3つの項目に、これから値を入れますよ」と宣言しているわけです。

そして、その下に`VALUES`という単語があります。VALUESは「値」という意味ですね。この後ろのカッコの中に、実際に入れたい値を順番に並べていきます。

`('山田太郎', 'taro@example.com', '東京都')`という部分が、実際のデータです。最初に指定した`name, email, prefecture`の順番と対応していますよね。nameには「山田太郎」、emailには「taro@example.com」、prefectureには「東京都」が入ります。

このSQL文を実行すると、customersテーブルに新しい行が1行追加されて、山田太郎さんのデータが記録される、という流れです。

ここで、実務的なポイントを1つお伝えしておきます。

私たちが第2回で学んだように、たいていのテーブルには「ID」という主キーがありましたよね。customer_idとか、order_idとか。でも、このINSERT文の中には、customer_idを指定していません。

これは、多くのデータベースで「IDは自動的に採番される」という仕組みになっているからです。私たちがわざわざ「次は123番だな」と計算しなくても、データベース側が「今まで122番まで使われているから、次は123番を割り振ろう」と自動でやってくれるんですね。

なので、INSERT文では、IDを除いた「実際に人間が入力する項目」だけを指定することが一般的です。もちろん、データベースの設定によっては手動でIDを指定する場合もありますが、基本的には「IDはシステムにお任せ」という感覚で大丈夫です。

では、ここでAIを使った例を見てみましょう。

画面を共有しますね。ChatGPTを開きます。

ここに、こんな風にプロンプトを入力してみます。

「顧客テーブルcustomersに、『鈴木一郎』『ichiro@example.com』『大阪府』という新規顧客を追加するSQLを書いてください。」

エンターキーを押します。

すると、AIが次のようなSQL文を返してくれました。

```sql
INSERT INTO customers (name, email, prefecture)
VALUES ('鈴木一郎', 'ichiro@example.com', '大阪府');
```

見事ですね。さきほどの山田太郎さんの例と、まったく同じ構造です。

日本語で「こういうデータを追加したい」と伝えるだけで、AIがSQL文に変換してくれる。これが、AI時代のSQL活用です。

もちろん、AIが返してきたSQLが100%正しいとは限りません。たとえば、テーブル名やカラム名を間違えていることもあります。でも、構造さえ理解していれば、「あ、ここはprefectureじゃなくてaddressカラムだな」とか、「customer_idじゃなくてuser_idだな」といった修正を、自分で依頼できるようになります。

つまり、皆さんに求められるのは、「SQLを完璧に暗記すること」ではなくて、「こういう構造なんだな、というイメージを持つこと」と、「AIに"こういうデータを追加して"と指示できること」なんです。

そして、もう1つ大事なポイント。

実際のシステムでは、INSERT文を直接実行することは、実はそんなに多くありません。たとえば、Webサイトで新規会員登録のフォームに名前やメールアドレスを入力してボタンを押すと、バックエンドのプログラムが自動的にINSERT文を組み立てて実行してくれます。

つまり、画面裏側でこの`INSERT INTO customers`が走っているわけですね。

非エンジニアの皆さんが、このINSERTのイメージを持っていると何が良いかというと、たとえば「新規登録機能を追加したい」とエンジニアに相談するときに、「ああ、この人はINSERTの話をしているんだな」と伝わるスピードが速くなります。

あるいは、「登録ボタンを押したけどエラーになった」というトラブルが起きたときに、「もしかして、必須項目が足りなくてINSERT文がエラーになってるのかな?」といった推測ができるようになるんです。

繰り返しになりますが、皆さんがSQLを完璧に書ける必要はありません。でも、「新しいデータを追加する=INSERT」という構造を知っているだけで、システム開発や運用の現場でのコミュニケーションが、ぐっとスムーズになります。

それでは次、UPDATEに進みましょう。

### 4-2. UPDATE:既存データを更新する(10分)

続いては、UPDATE。「更新」の命令です。

INSERTが「新しい行を追加する」だったのに対して、UPDATEは「既にある行の、特定のカラムの値を書き換える」という操作になります。

たとえば、お客さまがメールアドレスを変更したとき。あるいは、住所が変わったとき。注文のステータスを「発送待ち」から「発送済み」に変えたいとき。こういった「既存データの一部を変える」場面で使うのがUPDATEです。

画面に例を出しますね。

```sql
UPDATE customers
SET email = 'new_mail@example.com'
WHERE customer_id = 123;
```

順番に読んでいきましょう。

`UPDATE customers`。これは「customersテーブルを更新しますよ」という宣言です。

次に`SET email = 'new_mail@example.com'`。SETは「セットする」「設定する」という意味ですね。ここでは「emailカラムを、'new_mail@example.com'という値にセットしてください」と指示しています。

そして最後、`WHERE customer_id = 123`。ここが非常に重要です。WHEREは、さきほどSELECTのところで学びましたよね。「条件を指定する」部分でした。

このWHERE句があることで、「customer_idが123番のお客さま"だけ"のemailを書き換える」という意味になります。

もし、このWHERE句を書き忘れたらどうなるか。

想像してみてください。

```sql
UPDATE customers
SET email = 'new_mail@example.com';
```

これを実行すると、**customersテーブルの全顧客のemailが、すべて'new_mail@example.com'に書き換わってしまいます**。

全員のメールアドレスが同じになる。これは大事故ですよね。

実際、こういったミスは現場でも起こり得ます。特に本番環境のデータベースで、WHERE句なしのUPDATE文を実行してしまうと、取り返しのつかないことになります。

なので、UPDATEを書くときは、**必ずWHERE句をセットで書く**。これが鉄則です。

もちろん、皆さんが直接本番データベースを触ることは、ほとんどないと思います。でも、この「WHERE句を忘れると全件書き換わってしまう」という怖さを知っているだけで、エンジニアに依頼するときの言葉が変わってきます。

たとえば、「このお客さまのメールアドレスだけ変更してください」とお願いするとき、「customer_id=123の行だけ、という条件付きで」と伝えられるようになるわけです。

さて、ここでもう1つ実務的な話をしておきます。

本番環境のデータベースでは、UPDATEやDELETEといった「データを書き換える・消す」操作は、基本的に慎重に扱われます。

多くの会社では、「一般のメンバーは、本番DBに対して直接UPDATE文を実行しない」というルールになっています。代わりに、管理画面や専用のツールを使って、ログを残しながら更新する仕組みを作っているんですね。

あるいは、「UPDATE文を実行する前に、必ず別のエンジニアにレビューしてもらう」とか、「本番実行前に、テスト環境で動作確認する」といった運用フローが敷かれています。

つまり、UPDATEというのは「便利だけど、危険も伴う」命令なんです。

だからこそ、非エンジニアの皆さんも、「UPDATEがどういう動きをするのか」「WHERE句の大切さ」を理解しておくことが、リスク管理の第一歩になります。

では、AIを使ってUPDATE文を作ってもらう例を見てみましょう。

画面共有に戻ります。

ChatGPTに、こんな風に入力してみます。

「顧客テーブルcustomersで、customer_id=456の顧客の都道府県を『北海道』に変更するUPDATE文を書いてください。WHERE句を必ず含めて、安全に実行できる形でお願いします。」

少し長めのプロンプトですが、「WHERE句を必ず含めて」「安全に」という言葉を入れることで、AIにも「これは慎重に書かなきゃいけないな」と認識させることができます。

エンターを押すと、AIがこう返してくれました。

```sql
UPDATE customers
SET prefecture = '北海道'
WHERE customer_id = 456;
```

完璧ですね。ちゃんとWHERE句が付いています。

さらに、AIが補足説明も付けてくれています。「このSQL文は、customer_idが456のレコードのみを対象としています。WHERE句を必ず確認してから実行してください」といったコメントです。

このように、AIにお願いするときは、「安全に書いてほしい」「WHERE句は必須」といった条件を明示すると、より安心できるSQL文を返してくれます。

そして、もう1つ。

UPDATEは、1つのカラムだけでなく、複数のカラムをまとめて更新することもできます。

たとえば、

```sql
UPDATE customers
SET email = 'new_mail@example.com',
    prefecture = '神奈川県',
    updated_at = NOW()
WHERE customer_id = 123;
```

こんな風に、SETの後ろにカンマ区切りで複数の項目を並べることができます。

ここでは、emailとprefecture、さらにupdated_atという「更新日時」のカラムも一緒に書き換えています。`NOW()`は、現在の日時を取得する関数ですね。

「いつ更新されたか」を記録しておくことは、実務では非常に重要です。トラブルが起きたときに、「この顧客データ、最後に更新されたのはいつだっけ?」と確認できるからです。

多くのシステムでは、created_at(作成日時)とupdated_at(更新日時)という2つのカラムを持たせて、「いつ作られて、いつ最後に変更されたか」を自動記録する設計になっています。

非エンジニアの皆さんが、こういった「更新日時も一緒に記録する」という文化を知っているだけで、「ああ、このシステムは変更履歴がちゃんと残るんだな」という安心感につながりますし、逆に「変更日時が記録されていないシステム」に対して、「これ、あとで困らないかな?」という疑問を持てるようになります。

それでは、UPDATEのまとめです。

UPDATEは「既にある行の、特定のカラムを書き換える」命令。そして、**WHERE句は必須**。WHERE句がないと全件更新になってしまうので、非常に危険。

AIに依頼するときは、「WHERE句を含めて、安全に」と明示することで、より確実なSQL文を生成してもらえます。

では、次が最後、DELETEです。

### 4-3. DELETE:削除と「削除フラグ」の文化(10分)

それでは、いよいよ最後の命令、DELETE。「削除」です。

DELETEは、テーブルから行を消す命令です。文字通り、データを削除します。

基本的な書き方は、こうです。

```sql
DELETE FROM customers
WHERE customer_id = 123;
```

読み方は簡単ですね。

`DELETE FROM customers`で、「customersテーブルから削除してください」。

そして`WHERE customer_id = 123`で、「customer_idが123の行を」という条件指定です。

このSQL文を実行すると、customer_id=123の行が、テーブルから完全に消えます。

UPDATEのときにも言いましたが、ここでもWHERE句は絶対に必要です。

もしWHERE句を書き忘れたら、

```sql
DELETE FROM customers;
```

これを実行すると、**customersテーブルの全データが消えます**。

全顧客情報が一瞬で消える。これは、もう事故というレベルではなく、事件ですよね。

実際、こういったミスは過去に何度も起きていて、会社によっては「本番環境でDELETE文を直接実行することを禁止する」というルールを設けているところもあるくらいです。

ですから、DELETEは「最も慎重に扱うべき命令」と覚えておいてください。

さて、ここからが実務的に非常に重要な話になります。

今お見せしたDELETE文は、「物理削除」と呼ばれるものです。物理削除というのは、文字通り「データを物理的に消してしまう」という意味です。

一度消したデータは、基本的には元に戻せません。バックアップから復旧するしか方法がないんです。

でも、実際のビジネスシステムでは、「本当に完全に消してしまっていいのか?」という場面が多いんですね。

たとえば、お客さまが「退会します」と言ったとき。その顧客データを本当に消してしまっていいでしょうか?

もしかしたら、後日「やっぱり再登録したい」と戻ってくるかもしれません。あるいは、過去の注文履歴や問い合わせ履歴を確認したいという要望が出るかもしれません。

また、法律的な観点からも、「一定期間は顧客データを保管しておかなければならない」というルールがある業種もあります。

こういった理由から、多くのシステムでは「論理削除」という方法を採用しています。

論理削除というのは、「データは残しておくけれど、"削除された"という目印を付ける」という考え方です。

具体的には、テーブルに`is_deleted`というカラムを用意します。このカラムには、0か1の値を入れます。

* 0 = 有効(削除されていない)
* 1 = 削除済み(見えなくする)

そして、お客さまが退会したときは、DELETE文で消すのではなく、UPDATE文でis_deletedフラグを立てるんです。

```sql
UPDATE customers
SET is_deleted = 1
WHERE customer_id = 123;
```

こうすることで、データベース上には行が残りますが、「この顧客は削除済み」という情報が記録されます。

そして、通常の顧客一覧を取得するときは、SELECTにWHERE句を付けて、

```sql
SELECT *
FROM customers
WHERE is_deleted = 0;
```

「is_deletedが0、つまり有効な顧客だけを表示してください」という条件を必ず入れるわけです。

こうすれば、画面上では「退会済みのお客さま」は見えなくなりますが、データベースには残っているので、万が一のときに復旧したり、過去データを参照したりすることができます。

これが「論理削除」です。

実務では、論理削除のほうが圧倒的に多く使われています。物理削除は、本当に「もう二度と必要ない、完全に消していい」と確信できる場合だけです。

ちなみに、is_deletedだけでなく、`deleted_at`(削除日時)というカラムを一緒に持たせることも多いです。

たとえば、

```sql
UPDATE customers
SET is_deleted = 1,
    deleted_at = NOW()
WHERE customer_id = 123;
```

こうすることで、「いつ削除されたか」も記録できます。

「3年前に削除されたデータは、もう完全に物理削除していい」といったルールを設けている会社もありますし、「削除されてから1ヶ月以内なら、ユーザー自身が復活できる」といった機能を持つサービスもあります。

非エンジニアの皆さんが、この「削除フラグ」の文化を知っていると、何が良いかというと、

まず、「削除=完全に消える」ではなく、「見えなくするだけ」という選択肢があることを理解できます。

そして、エンジニアと「削除機能を作りたいんですが」という会話をするときに、「これは物理削除でいいのか、論理削除にすべきか」という論点を持てるようになります。

さらに、「削除したデータを復活させたい」という要望が出たときにも、「論理削除にしておけばよかった」と気づけるわけです。

では、ここでもAIを活用してみましょう。

画面共有に戻ります。

ChatGPTに、こんなプロンプトを入れてみます。

「顧客テーブルcustomersに、is_deletedカラムがあります。customer_id=789の顧客を論理削除(フラグを立てる)するUPDATE文を書いてください。また、deleted_atに現在日時も記録してください。」

エンターを押すと、

```sql
UPDATE customers
SET is_deleted = 1,
    deleted_at = NOW()
WHERE customer_id = 789;
```

こういうSQL文が返ってきました。

さらに、AIが「このSQL文は論理削除を行います。実際にデータは削除されず、is_deletedフラグが1にセットされるため、後から復旧することも可能です」といった説明も付けてくれています。

この説明文も含めて、エンジニアに共有すれば、「ああ、この人は論理削除を理解しているな」と伝わりますよね。

逆に、「本当に物理削除していいケース」も確認してみましょう。

「顧客テーブルcustomersから、テストユーザー(customer_id=999)のデータを完全に削除するDELETE文を書いてください。ただし、本番環境では実行しないよう注意書きも添えてください。」

こうプロンプトすると、

```sql
-- 注意:これは物理削除です。本番環境では実行しないでください。
DELETE FROM customers
WHERE customer_id = 999;
```

こんな風に、コメント付きで返してくれます。

SQLの中で、`--`で始まる行は「コメント」です。プログラムとしては実行されない、メモ書きのようなものですね。

こうやって、「これは危険な操作だよ」というメッセージを、SQL文の中に残しておくこともできるわけです。

さて、DELETEのまとめです。

DELETEは「行を完全に消す」物理削除の命令。WHERE句は絶対必須。

でも、実務では「論理削除」、つまり「is_deletedフラグを立てるだけ」という方法が主流。

データを完全に消すのは怖いので、「見えなくするだけ」にしておいて、必要なときに復旧できるようにする。これが安全なシステム設計の考え方です。

そして、AIにお願いするときは、「物理削除なのか、論理削除なのか」を明確に伝えると、より適切なSQL文を生成してもらえます。

### 4-4. AIに安全なSQLを書かせるコツ(5分)

それでは、このセクションの最後に、「AIに安全なSQLを書かせるコツ」をまとめておきましょう。

ここまで、INSERT、UPDATE、DELETEという3つの「書き込み系」の命令を見てきました。

これらは、どれも「データを変更する」命令なので、使い方を間違えると大きな事故につながります。

でも、AIを上手に活用すれば、私たち非エンジニアでも、安全で正確なSQL文を作ることができます。

そのためのポイントを、3つお伝えします。

**ポイント1:「安全に」「WHERE句必須で」と明示する**

AIは、こちらの指示に忠実に応えてくれます。

なので、「UPDATE文を書いて」とだけ言うのではなく、「WHERE句を必ず含めて、安全に実行できるUPDATE文を書いてください」と明示しましょう。

「本番データなので、誤って全件更新にならないように注意してください」といった一文を添えるだけでも、AIの出力が変わってきます。

画面に例を出しますね。

```
顧客テーブルcustomersがあります。
本番データなので、誤って全件更新や削除にならないように、
WHERE句を必ず付けたUPDATE文とDELETE文の例を、それぞれ1つずつ示してください。
また、それぞれのSQLの意図も日本語で説明してください。
```

こういうプロンプトを投げると、AIは次のような形で返してくれます。

```sql
-- 特定顧客のメールアドレスを更新
UPDATE customers
SET email = 'updated@example.com'
WHERE customer_id = 123;

-- 特定顧客を削除
DELETE FROM customers
WHERE customer_id = 456;
```

そして、それぞれに「このSQLは、customer_idが123の顧客のみを対象としています」といった説明が付きます。

こうやって、「安全性を意識したSQL」をAIに要求することが、第一のポイントです。

**ポイント2:テーブル構造をAIに伝える**

AIは、皆さんの会社のデータベース構造を知りません。

なので、「どんなテーブルがあって、どんなカラムがあるか」を事前に伝えると、より正確なSQLを生成してくれます。

たとえば、

```
顧客テーブルcustomersは、次のカラムを持っています:
- customer_id (主キー)
- name (顧客名)
- email (メールアドレス)
- prefecture (都道府県)
- is_deleted (削除フラグ、0=有効、1=削除済み)
- created_at (登録日時)
- updated_at (更新日時)

この構造で、東京都の顧客だけを取得するSELECT文を書いてください。
```

こういう風に、テーブル定義を先に渡してあげると、AIは「ああ、このテーブルにはprefectureカラムがあるんだな」と理解して、正確なSQL文を作ってくれます。

逆に、テーブル構造を伝えずに「顧客を取得して」とだけ言うと、AIは一般的な推測でSQL文を作るので、実際のカラム名と合わないことがあります。

ですから、できるだけ「このテーブルには、こういう項目がありますよ」という情報をセットで渡すことが、第二のポイントです。

**ポイント3:出力されたSQLを「読む」習慣をつける**

AIが返してくれたSQL文を、そのままコピーして実行する前に、一度「読む」習慣をつけましょう。

完璧に理解できなくても大丈夫です。

「あ、これはUPDATE文だな」「WHERE句はちゃんと付いているな」「更新しているのはemailカラムか」といった、大まかな構造を確認するだけでも、事故を防ぐことができます。

そして、もし「あれ、このカラム名、ちょっと違う気がする」と気づいたら、すぐにAIに聞き直せばいいんです。

「さっきのSQL、prefectureカラムじゃなくてaddressカラムを使ってください」と修正依頼すれば、AIはすぐに書き直してくれます。

この「生成→確認→修正依頼」のサイクルを回すことで、どんどん精度が上がっていきます。

非エンジニアの皆さんに求められるのは、「SQLを完璧に書けること」ではなく、「AIが生成したSQLを、ざっくり読めて、おかしいところに気づけること」なんです。

それができれば、エンジニアに依頼するときも、「このSQL文でお願いします」とスムーズに伝えられますし、逆に「このSQL、WHERE句がないけど大丈夫ですか?」と確認することもできます。

まとめると、AIに安全なSQLを書かせるコツは、

1. 「安全に」「WHERE句必須で」と明示する
2. テーブル構造をAIに伝える
3. 出力されたSQLを「読む」習慣をつける

この3つです。

そして、何より大事なのは、「失敗を恐れすぎない」こと。

もちろん、本番環境で適当にSQLを実行するのは絶対NGです。でも、学習段階では、どんどんAIに質問して、試して、エラーを見て、修正して、というプロセスを繰り返してください。

## セクション4 全体の締めくくり

さて、ここまでで、SQLの「書き込み系」の3つの命令、INSERT、UPDATE、DELETEを見てきました。

最後に、もう一度整理しておきましょう。

**INSERT**は、新しい行を追加する命令。新規顧客登録、新規注文など、「データを増やす」場面で使います。IDは自動採番されることが多いので、人間が入力する項目だけを指定すればOK。

**UPDATE**は、既にある行の値を書き換える命令。メールアドレス変更、ステータス更新など、「データを変える」場面で使います。WHERE句は絶対必須。WHERE句がないと全件書き換わってしまうので、非常に危険。

**DELETE**は、行を削除する命令。物理削除として使うと、データが完全に消えます。でも、実務では「論理削除」、つまりis_deletedフラグを立てるだけの方法が主流。データを完全に消すのは怖いので、「見えなくするだけ」にしておく文化がある。

そして、これらのSQLをAIに書いてもらうときは、「安全に」「WHERE句必須で」と明示する。テーブル構造を伝える。生成されたSQLを読む習慣をつける。この3つを意識すれば、非エンジニアでも十分にSQLを活用できます。

繰り返しになりますが、皆さんに求められるのは、「SQLを暗記すること」ではありません。

「こういう操作がしたい」という日本語を、AIにSQL文に変換してもらう。そして、そのSQL文がどういう動きをするのか、ざっくりイメージできる。WHEREが付いているか、更新対象は正しいか、といった基本的なチェックができる。

それだけで十分です。

そして、もし間違ったSQL文を実行してしまっても、バックアップがあれば復旧できます。もちろん、本番環境では慎重に、テスト環境で確認してから、という手順を踏むことが大事ですが、学習段階では、どんどん試して、失敗して、学んでいってください。

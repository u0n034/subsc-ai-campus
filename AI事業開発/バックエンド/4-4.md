# 第4回「4. JSONというデータ形式 – 「人にも機械にも読める」データの形」ナレーション原稿

## 4-1. JSONの基本形を読む(10分)

それでは、ここからは「JSON」という、バックエンドの世界では欠かせないデータの形式について学んでいきましょう。

JSONという言葉、聞いたことがある方もいらっしゃるかもしれません。でも、「なんとなく聞いたことはあるけれど、実際に何なのかはよくわからない」という方がほとんどではないでしょうか。

安心してください。JSONは、見た目はちょっと独特ですが、その本質は非常にシンプルです。今日のこのセクションを終える頃には、「ああ、JSONってこういうものか」と、自信を持って理解できるようになっているはずです。

### JSONとは何か

まず、JSONとは何かを一言で説明すると、「データを構造化して表現するための形式」です。もっと噛み砕いて言えば、「人間が読めて、機械も読める、データの書き方のルール」ということになります。

JSONという名前は、「JavaScript Object Notation」の略です。もともとはJavaScriptというプログラミング言語で使われていた書き方なのですが、今では言語を問わず、世界中のシステムで標準的に使われています。

なぜJSONがこれほど広まったのでしょうか。それは、JSONが持つ3つの特徴のおかげです。

1つ目は、「人間が読みやすい」こと。データベースの中身やプログラムの内部データは、通常は人間には読めない形式で保存されていることが多いのですが、JSONは文字で書かれているので、エンジニアでなくても、少し慣れれば内容を理解できます。

2つ目は、「機械が処理しやすい」こと。JSONには明確なルールがあるので、プログラムがこれを読み込んで、自動的にデータとして扱うことができます。

そして3つ目は、「シンプルで軽量」であること。余計な装飾がなく、必要最小限の記号だけで構造を表現できるので、ネットワークを通じてデータをやり取りする際に効率的なのです。

### 実際のJSONを見てみましょう

それでは、実際にJSONがどんな見た目をしているのか、画面に表示してみましょう。

```json
{
  "id": 123,
  "name": "田中太郎",
  "email": "taro.tanaka@example.com",
  "prefecture": "石川県",
  "is_active": true
}
```

これが、JSONの最もシンプルな例です。

第一印象として、「なんだか記号が多いな」と感じるかもしれません。でも、落ち着いて見ていきましょう。実はこれ、第2回で学んだ「顧客テーブル」の1レコード分のデータを、別の形で表現しているだけなんです。

### JSONの構造を分解する

それでは、このJSONを1つずつ分解して見ていきましょう。

まず、全体を囲んでいる波括弧、`{` と `}` に注目してください。この波括弧は、「ここからここまでが1つのまとまりですよ」という印です。データベースで言えば、「1レコード」「1行のデータ」を表していると考えてください。

この波括弧の中に、いくつかの行が並んでいますね。1行ずつ見ていきましょう。

```json
"id": 123
```

この行を見てください。`"id"` と書かれている部分、これを「キー」と呼びます。データベースで言えば、「カラム名」「項目名」にあたるものです。

そして、コロン `:` の後ろにある `123` が「値」です。この顧客のIDは123番ですよ、という情報を表しています。

次の行も同じ構造です。

```json
"name": "田中太郎"
```

キーが `"name"`、値が `"田中太郎"` です。この顧客の名前は田中太郎さんですよ、という意味ですね。

ここで1つ、重要な違いに気づきましたか？ `123` と `"田中太郎"` の書き方が違いますよね。

`123` は、ダブルクォーテーション（引用符）で囲まれていません。これは「数値」を表しています。

一方、`"田中太郎"` は、ダブルクォーテーションで囲まれています。これは「文字列」を表しています。

JSONでは、データの種類によって書き方が変わるんです。これは、第3回でSQLを学んだときと似ていますね。SQLでも、文字列はシングルクォーテーションで囲む必要がありましたよね。

### JSONのデータ型

それでは、このサンプルに出てくるデータ型を整理してみましょう。

まず、「数値」です。

```json
"id": 123
```

これはそのまま数字として書きます。引用符は不要です。整数でも小数でも、同じように書けます。たとえば `"price": 1980` とか、`"rating": 4.5` といった具合です。

次に、「文字列」です。

```json
"name": "田中太郎",
"email": "taro.tanaka@example.com",
"prefecture": "石川県"
```

文字列は必ずダブルクォーテーションで囲みます。これがルールです。人の名前、メールアドレス、住所など、文字で表現されるデータはすべてこの形式になります。

そして、もう1つ、このサンプルには特殊なデータ型が登場しています。

```json
"is_active": true
```

この `true` という値、見慣れない方もいるかもしれません。これは「真偽値」または「ブール値」と呼ばれるもので、「正しい」「有効」という意味を表します。

反対の意味を表すには、`false` を使います。`false` は「間違っている」「無効」という意味です。

この `is_active` というキーは、「このユーザーが現在有効かどうか」を示しています。`true` なら有効、`false` なら退会済みや無効状態、といった使い方をします。

真偽値は、引用符で囲みません。`true` と `false`、この2つだけが特別な値として認識されます。

### JSONはテーブルの別の見せ方

ここまでの説明で、JSONの基本的な構造は理解できたでしょうか。

改めて整理すると、JSONというのは、データベースのテーブルで言えば「1レコード分のデータ」を、キーと値のペアで表現したものなんです。

第2回で学んだ顧客テーブルを思い出してください。

| id  | name   | email                       | prefecture | is_active |
| --- | ------ | --------------------------- | ---------- | --------- |
| 123 | 田中太郎 | taro.tanaka@example.com | 石川県      | true      |

このテーブルの1行が、先ほどのJSONと完全に対応していますよね。

つまり、JSONは「テーブルの別の見せ方」だと考えればいいんです。

データベースの中では、データは表形式で管理されています。でも、その情報をインターネット経由で別のシステムに送ったり、プログラムで処理したりするときには、この表をそのまま送るわけにはいきません。

そこで、「この顧客のデータはこういう内容ですよ」という情報を、文字列として表現する必要があります。それがJSONなんです。

非エンジニアの皆さんは、JSONを見たときに、「ああ、これはテーブルの1行を別の形で書いたものだな」と理解できれば十分です。

実際にJSONを書く必要はありません。それはAIやプログラムがやってくれます。でも、「これが何を意味しているのか」を読み取れることが大切なんです。

### なぜバックエンドでJSONが使われるのか

ここまでJSONの形を見てきましたが、「なぜバックエンドの世界でこんなにJSONが使われるのか」について、もう少し掘り下げてみましょう。

先ほど少し触れましたが、バックエンドとフロントエンドの間では、データのやり取りが頻繁に行われます。

たとえば、スマホアプリで「顧客一覧」を表示するとき、アプリ側（フロントエンド）は、サーバー（バックエンド）に「顧客データをください」とリクエストします。

バックエンドは、データベースから顧客情報を取り出して、それをフロントエンドに返します。このとき、「どういう形式でデータを返すか」が問題になるわけです。

昔は、XMLという形式がよく使われていました。でも、XMLは記述が冗長で、データ量が大きくなりがちでした。

それに対してJSONは、必要最小限の記号だけでデータを表現できるので、軽量で高速です。しかも、人間にも読みやすい。だから、今ではJSON が事実上の標準になっているんです。

つまり、REST APIでデータをやり取りする際、レスポンスとして返ってくるデータは、ほぼ間違いなくJSON形式になっている、ということです。

### もう一度、サンプルを見直す

それでは、もう一度、最初のサンプルを見てみましょう。

```json
{
  "id": 123,
  "name": "田中太郎",
  "email": "taro.tanaka@example.com",
  "prefecture": "石川県",
  "is_active": true
}
```

今度は、このJSONを見て、「ああ、これは顧客テーブルの田中太郎さんのレコードを表しているんだな」と、自然に理解できるのではないでしょうか。

各行の最後にカンマ `,` がついていることにも注目してください。これは、「次にもまだキーと値のペアが続きますよ」という印です。

ただし、最後の行にはカンマがついていません。これがJSONのルールです。最後の項目の後ろにはカンマを付けない、と覚えておいてください。

もし間違ってカンマを付けてしまったり、逆に必要な場所でカンマを忘れてしまうと、JSONとして正しく認識されず、エラーになります。

でも、安心してください。AIにJSONを生成してもらう場合は、こうした細かいルールは自動的に守られます。私たちが覚える必要があるのは、「こういうルールがあるんだな」という程度で十分です。

### JSONは怖くない

ここまでの説明で、JSONの基本形は理解できたでしょうか。

最初は記号が多くて「難しそう」と感じたかもしれません。でも、実際には非常にシンプルな構造です。

波括弧で囲んで、キーと値をコロンでつなぎ、カンマで区切る。ただそれだけです。

そして、このJSONは、私たちが第2回で学んだテーブルの「別の見せ方」に過ぎません。

次のセクションでは、複数のレコード、つまり「複数行のデータ」をJSONでどう表現するのかを見ていきます。そして、さらにその先では、テーブル同士の関係をJSONでどう表すのか、という少し複雑な構造にも触れていきます。

でも、基本はこの形です。この波括弧の構造さえ理解できれば、あとは応用なんです。

それでは、次に進みましょう。

## 4-2. 配列とネスト – 複数件＆入れ子構造(8分)

それでは、ここからは、JSONでもう少し複雑なデータを表現する方法を学んでいきましょう。

先ほどのセクションでは、顧客1人分のデータ、つまり「1レコード」をJSONで表現する方法を見ました。

でも、実際のシステムでは、1件のデータだけを扱うことは稀です。顧客一覧を取得したり、注文履歴を複数件取得したり、といったように、「複数のレコード」を一度にやり取りすることの方が圧倒的に多いんです。

では、複数のデータをJSONでどう表現するのでしょうか。

### 配列 – 複数のデータをまとめる

JSONで複数のデータを表現するときには、「配列」という仕組みを使います。

配列という言葉、聞いたことがある方もいるかもしれません。英語では「Array」と言います。簡単に言えば、「データのリスト」「データの集まり」のことです。

実際に見てみましょう。

```json
[
  {
    "id": 1,
    "name": "田中太郎"
  },
  {
    "id": 2,
    "name": "佐藤花子"
  }
]
```

これが、JSONで複数のデータを表現した例です。

先ほどとの違いがわかりますか？ 全体を囲んでいるのが、波括弧 `{}` ではなく、角括弧 `[]` になっていますね。

この角括弧が、「配列」を表す記号です。「ここからここまでが、複数のデータのまとまりですよ」という印なんです。

そして、その中に、波括弧で囲まれたデータが2つ並んでいます。1つ目が田中太郎さん、2つ目が佐藤花子さんです。

2つのデータの間には、カンマ `,` で区切られています。これは、「次にもまだデータが続きますよ」という印です。

### 配列は「複数行の表」

この配列の構造を、データベースのテーブルに対応させて考えてみましょう。

先ほどのJSONは、こういうテーブルを表していることになります。

| id | name   |
| -- | ------ |
| 1  | 田中太郎 |
| 2  | 佐藤花子 |

つまり、角括弧 `[]` は、「複数行の表」を表しているんです。

そして、その中の1つ1つの波括弧 `{}` が、それぞれ「1行のレコード」を表している、というわけです。

このように考えると、配列も決して難しくありませんよね。

実際のシステムでは、たとえば `GET /customers` というAPIを呼び出すと、こういった配列形式のJSONが返ってきます。顧客が100人いれば、波括弧のブロックが100個並ぶことになります。

### 配列の中身はいくつでも

配列の中には、データをいくつでも入れることができます。

```json
[
  { "id": 1, "name": "田中太郎" },
  { "id": 2, "name": "佐藤花子" },
  { "id": 3, "name": "鈴木一郎" },
  { "id": 4, "name": "高橋美咲" }
]
```

このように、4件、5件、100件と、必要なだけデータを並べることができます。

ただし、データが大量になる場合は、一度にすべてを返すのではなく、「ページング」という仕組みを使います。たとえば、「最初の10件だけ」「次の10件」というように、少しずつデータを取得していくわけです。

でも、その場合も、返ってくるJSON自体は配列形式で、その中に10件分のデータが入っている、という構造に変わりはありません。

### ネスト構造 – データの中にデータ

それでは、さらにもう一歩進んで、「ネスト構造」について触れておきましょう。

ネストというのは、「入れ子」という意味です。つまり、「データの中に、さらにデータが入っている」という構造のことです。

たとえば、顧客のデータに、その顧客が過去に行った注文の情報も一緒に含めたい、という場合を考えてみましょう。

```json
{
  "id": 1,
  "name": "田中太郎",
  "email": "taro.tanaka@example.com",
  "orders": [
    {
      "order_id": 101,
      "product": "ノートPC",
      "price": 98000
    },
    {
      "order_id": 102,
      "product": "マウス",
      "price": 2980
    }
  ]
}
```

このJSONを見てください。

顧客の基本情報である `id`、`name`、`email` の下に、`orders` というキーがあります。

そして、その値として、角括弧 `[]` で囲まれた配列が入っています。つまり、「注文のリスト」がここに埋め込まれているわけです。

その配列の中には、注文ごとのデータが波括弧 `{}` で表現されています。注文ID、商品名、価格といった情報が、それぞれの注文ごとに記録されているんですね。

このように、「顧客」というデータの中に、「注文」という別のデータが配列として含まれている状態を、「ネスト構造」と呼びます。

### ネスト構造とテーブルの関係

このネスト構造は、第2回で学んだ「テーブル同士の関係」と深く結びついています。

顧客テーブルと注文テーブルは、「1対多」の関係でしたよね。1人の顧客が、複数の注文を持つことができる、という関係です。

JSONでこの関係を表現すると、顧客の中に注文の配列を入れる、という形になるわけです。

ただし、ここで1つ注意があります。

実際のデータベース設計では、顧客テーブルと注文テーブルは別々に存在しています。それらを「外部キー」で結びつけているんでしたよね。

では、なぜJSONではこうしたネスト構造が使われるのでしょうか。

それは、「データを取得する側の便利さ」のためです。

たとえば、画面に「顧客の詳細情報と、その顧客の注文履歴」を同時に表示したい場合を考えてみましょう。

もし、顧客情報と注文情報を別々のAPIで取得しなければならないとしたら、2回のリクエストが必要になります。これは効率が悪いですよね。

そこで、バックエンド側であらかじめ顧客情報と注文情報を結合して、1つのJSONにまとめて返す、という設計がよく使われるんです。

これによって、フロントエンド側は1回のリクエストで必要な情報をすべて取得できます。

### ネスト構造は第5回以降でまた出てくる

今日は、ネスト構造の存在を知っておく、という程度で十分です。

実際に、こうした複雑な構造のJSONを設計するのは、第5回、第6回で、実際のミニアプリケーションを作るときに取り組んでいきます。

今の段階では、「JSONは、配列を使って複数のデータをまとめることができる」「データの中に別のデータを入れ子にすることもできる」ということを理解できていれば十分です。

### 配列とネストのまとめ

それでは、ここまでのポイントを整理しましょう。

1つ目、角括弧 `[]` は配列を表します。これは「複数行のデータ」「リスト」を意味します。

2つ目、配列の中には、波括弧 `{}` で囲まれたデータを複数並べます。それぞれが1レコード分のデータです。

3つ目、データの中に別のデータを入れ子にすることができます。これをネスト構造と呼びます。

4つ目、ネスト構造は、テーブル同士の関係を表現する際によく使われます。

この4点を押さえておけば、実際にAPIのレスポンスとしてJSONが返ってきたときに、「ああ、これは複数の顧客データが入っているんだな」「この中には注文情報も含まれているんだな」と、構造を読み取ることができるようになります。

## 4-3. JSON ↔ テーブルの対応をAIにやらせる(7分)

それでは、最後のセクションです。ここでは、実際にAIを使って、「テーブルのデータをJSONに変換する」という作業を体験してみましょう。

これまで、JSONの形や配列、ネスト構造といった概念を学んできました。でも、実際に自分の手でJSONを書く必要はありません。それはAIに任せればいいんです。

私たちが理解すべきなのは、「テーブルとJSONがどう対応しているか」というイメージです。そして、「AIにどういう指示を出せば、欲しいJSONを作ってもらえるか」という、ディレクション能力なんです。

### テーブルからJSONへの変換

それでは、第2回で扱った顧客テーブルをもう一度思い出してください。

顧客テーブルには、次のようなカラムがありました。

- id(数値)
- name(文字列)
- email(文字列)
- prefecture(都道府県名)
- is_active(true/false)

このテーブルに、実際のデータが3件入っているとしましょう。

| id  | name   | email                       | prefecture | is_active |
| --- | ------ | --------------------------- | ---------- | --------- |
| 1   | 田中太郎 | taro.tanaka@example.com | 石川県      | true      |
| 2   | 佐藤花子 | hanako.sato@example.com | 東京都      | true      |
| 3   | 鈴木一郎 | ichiro.suzuki@example.com | 大阪府      | false     |

この3件のデータを、REST APIのレスポンスとして返すことを想定して、JSON形式に変換したい、という状況を考えます。

もし、自分の手でJSONを書くとなると、波括弧や角括弧、カンマの位置など、細かいルールを気にしながら入力していく必要があります。これは、非エンジニアにとっては負担が大きいですよね。

そこで、AIの出番です。

### AIへのプロンプト例

AIに対して、次のようなプロンプトを投げてみましょう。

```
次の顧客テーブルを、REST APIのレスポンスとして返すことを想定して、
JSONのサンプルデータを3件分作ってください。

- id(数値)
- name(文字列)
- email(文字列)
- prefecture(都道府県名)
- is_active(true/false)

データの内容は、日本人の名前と、実在しそうなメールアドレス、
日本の都道府県名で作成してください。
```

このプロンプトを見てください。

ポイントは、「テーブルの構造」を明確に伝えていることです。カラム名とデータ型を箇条書きで示しています。

そして、「JSONのサンプルデータを3件分作ってください」と、具体的に何をしてほしいのかを指示しています。

さらに、「日本人の名前」「実在しそうなメールアドレス」といった、データの内容に関する条件も加えています。これによって、AIはより現実的なサンプルデータを生成してくれます。

### AIの回答例

AIにこのプロンプトを投げると、おそらく次のようなJSONを返してくれるはずです。

```json
[
  {
    "id": 1,
    "name": "田中太郎",
    "email": "taro.tanaka@example.com",
    "prefecture": "石川県",
    "is_active": true
  },
  {
    "id": 2,
    "name": "佐藤花子",
    "email": "hanako.sato@example.com",
    "prefecture": "東京都",
    "is_active": true
  },
  {
    "id": 3,
    "name": "鈴木一郎",
    "email": "ichiro.suzuki@example.com",
    "prefecture": "大阪府",
    "is_active": false
  }
]
```

どうでしょうか。私たちが意図した通りの構造で、3件分のデータがJSON形式で出力されていますね。

角括弧で全体が囲まれていて、その中に3つの波括弧のブロックが並んでいます。各ブロックには、id、name、email、prefecture、is_activeの5つのキーが含まれています。

数値はそのまま、文字列はダブルクォーテーションで囲まれ、真偽値はtrueまたはfalseで表現されています。

このように、AIに適切な指示を出せば、私たちが手を動かすことなく、正しいJSON形式のデータを生成してもらえるんです。

### テーブル → JSON の変換は自動化できる

ここで重要なポイントをお伝えします。

実際のバックエンドシステムでは、この「テーブルのデータをJSONに変換する」という処理は、プログラムによって自動的に行われます。

データベースからSQLでデータを取得して、それをJSON形式に変換して、APIのレスポンスとして返す。この一連の流れは、バックエンドのフレームワークが自動的にやってくれるんです。

つまり、エンジニアも、実際には手作業でJSONを書いているわけではありません。

ただし、「どういう構造のJSONを返すべきか」を設計する段階では、こうしたサンプルデータを作って、関係者間でイメージを共有することが非常に重要です。

たとえば、フロントエンドのエンジニアに「こういう構造のJSONが返ってくるので、それを前提に画面を作ってください」と伝えるときに、実際のサンプルJSONがあると、認識のズレがなくなります。

また、外部のシステムとデータ連携をする際にも、「うちのAPIはこういうJSON形式でデータを返します」というドキュメントを作る必要があります。

そうした場面で、AIにサンプルJSONを作ってもらうことができれば、非エンジニアでも設計段階からプロジェクトに参加できるわけです。

### JSON → テーブル の逆変換もできる

逆に、「すでにあるJSONを見て、それに対応するテーブル構造を考える」という作業も、AIに頼むことができます。

たとえば、外部のAPIから返ってきたJSONがあって、それを自社のデータベースに取り込みたい、という状況を考えてみましょう。

そのときには、次のようなプロンプトを使います。

```
次のJSONデータを、データベースのテーブルとして保存したいです。
適切なテーブル構造を提案してください。

[ここにJSONを貼り付ける]

テーブル名、カラム名、データ型を含めた定義を、
CREATE TABLE文の形で出力してください。
```

このプロンプトを投げると、AIは、JSONの構造を分析して、それに対応するテーブル定義を作ってくれます。

配列になっている部分は別テーブルに分ける、ネスト構造は外部キーで関連づける、といった設計判断も、AIがある程度提案してくれます。

もちろん、最終的な設計判断はエンジニアと相談する必要がありますが、たたき台としてAIに作ってもらうことで、会話のスタート地点が格段に上がります。

### JSONは「テーブルの別の見せ方」という理解

ここまでの説明で、おそらくこういう理解に到達できたのではないでしょうか。

「JSONというのは、結局、テーブルのデータを別の形で表現したものだ。テーブルが表形式なら、JSONはキーと値のペアで構造化された形式だ。でも、本質的には同じデータを指している」

この理解が、非エンジニアにとって最も重要です。

エンジニアは、JSONの細かい文法や、特殊なケースの扱い方といった技術的な詳細を知っている必要があります。

でも、非エンジニアは、「JSONはテーブルの別の見せ方」というイメージを持っていれば十分です。

そして、AIを使って、テーブルとJSONの間を自由に行き来できる、という実感を持てたなら、それだけで大きな前進です。

### 実務での活用イメージ

それでは、実務でこの知識をどう活かせるか、いくつか例を挙げてみましょう。

1つ目は、「API設計のレビュー」です。

エンジニアが作ったAPI設計書を見たときに、「このエンドポイントは、こういうJSONを返すんですね」という記述があれば、それを見て、「ああ、顧客テーブルの情報が入っているんだな」「注文情報も一緒に返ってくるんだな」と理解できます。

もし、「この項目も入れてほしい」「この情報は不要では?」といったフィードバックがあれば、エンジニアに伝えることができます。

2つ目は、「外部連携の仕様確認」です。

他社のシステムとAPI連携をする際、先方から「うちのAPIはこういうJSONを返します」という仕様書が送られてくることがあります。

そのJSONを見て、「これは顧客の情報なんだな」「複数件が配列で返ってくるんだな」と理解できれば、自社のエンジニアに「この情報を使って、うちのDBのどのテーブルに格納すればいいですか?」という質問ができます。

3つ目は、「ダッシュボードやBIツールへのデータ連携」です。

社内のデータを可視化するために、BIツールにAPIでデータを送る、という場面があります。

そのとき、「どういうJSON形式でデータを送るべきか」という仕様を決める必要があります。非エンジニアでも、AIを使ってサンプルJSONを作り、「こういう形でデータを送りたいです」とエンジニアに提案できれば、プロジェクトがスムーズに進みます。

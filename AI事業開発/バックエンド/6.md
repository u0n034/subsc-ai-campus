## 第6回：ミニCRUDアプリ② – API設計とAIコード生成を見る（2時間）詳細構成案【収録版】

### この回のゴール

* 第5回で作った**テーブル設計・ER図**をもとに、
  「どんなAPI（エンドポイント）が必要か？」を自分の言葉で説明できるようになる
* **CRUD（Create/Read/Update/Delete）とAPIの関係**を、具体的なURL・HTTPメソッドでイメージできる

  * API一覧

### 2. CRUDとAPIの関係おさらい（15分）

**目的：**
CRUDとAPI設計を結びつけ、「何を作ればいいか」の全体像を掴む

**2-1. CRUDの再確認（7分）**

* スライドでCRUDを再掲：

  * Create：新規登録（例：問い合わせを登録）
  * Read：参照（例：問い合わせ一覧を見る／詳細を見る）
  * Update：更新（例：ステータスや担当者を変更）
  * Delete：削除（例：論理削除で “無効化” する など）

* **DBの操作とAPIの関係を線でつなぐ図**

  * `POST /inquiries` → inquiriesテーブルに新規行（Create）
  * `GET /inquiries` → inquiriesテーブルから読み出し（Read）
  * `PUT /inquiries/{id}` → 該当行を更新（Update）
  * `DELETE /inquiries/{id}` → 削除 or 無効化（Delete）

**2-2. HTTPメソッドとの対応表（8分）**

* シンプルな対応表を画面に表示：

  | 操作     | 代表的なHTTPメソッド |
  | ------ | ------------ |
  | データの取得 | GET          |
  | 新規作成   | POST         |
  | 全体更新   | PUT          |
  | 一部更新   | PATCH        |
  | 削除     | DELETE       |

* ナレーションポイント：

  * 「実務では、**完全一致ではない場合もあります**（例えばPATCHを使わずPUTだけで済ませるなど）」
  * 「今日は“教科書的な対応”を押さえつつ、実務での揺れも軽く触れます」

### 3. エンドポイント一覧の設計ワーク（25分）

**目的：**
第5回で設計したテーブル構成から、必要なAPIエンドポイント一覧を自分たちで設計する流れを体験する

**3-1. “このシステムで最低限ほしい操作”を整理（10分）**

* スライドで、問い合わせ管理システムの主な操作を列挙：

  * 問い合わせを新規登録する
  * 問い合わせの一覧を表示する（フィルタ・ソート含む）
  * 問い合わせの詳細を表示する
  * ステータスを変更する
  * コメントを追加する
  * カテゴリ一覧を取得する

* ナレーション例：

  * 「**画面側でやりたいことの数だけ、“裏で必要なAPI”がいるイメージ**です」
  * 「ここでの“抜け漏れチェック”が、後々の手戻りを防ぎます」

**3-2. AIにエンドポイント一覧を提案させるデモ（15分）**

* 実際のプロンプト例：

  ```text
  社内の問い合わせ管理システムのAPIを設計したいです。

  データベースは、以下のようなテーブル構成を想定しています。

  - users（ユーザー）
  - inquiries（問い合わせ）
  - inquiry_categories（問い合わせカテゴリ）
  - inquiry_comments（問い合わせコメント）

  このシステムの主な機能は、次のとおりです。

  - 社員が問い合わせを新規登録する
  - 問い合わせの一覧を表示する（ステータスやカテゴリで絞り込みできる）
  - 問い合わせの詳細を表示する
  - 問い合わせのステータスや担当者を更新する
  - 問い合わせにコメントを追加する
  - 問い合わせカテゴリ一覧を取得する

  この前提で、
  「HTTPメソッド」「URLパス」「概要説明」を含む
  REST APIのエンドポイント一覧を表形式で提案してください。
  ```

* 画面にAI回答（表形式）を映しながら解説：

  * 「AIが出してきた一覧を、“実際の業務フローに合っているか”の目線でチェックします」
  * 「例えば、`GET /inquiries/{id}/comments` があると、“詳細画面でコメントだけ後から読み込む”こともできますね、など」

### 4. リクエスト・レスポンス設計とJSONの読み方（25分）

**目的：**
非エンジニアでも、JSONの中身を見て「何が送られ・返ってくるか」を理解できるようにする

**4-1. 代表エンドポイントをピックアップ（10分）**

* 例として、以下の3つを採用：

  * `POST /inquiries`（問い合わせ新規登録）
  * `GET /inquiries`（問い合わせ一覧取得）
  * `POST /inquiries/{id}/comments`（コメント追加）

* 1つずつ、**どんな情報が必要そうか**をホワイトボード風に書き出す：

  * `POST /inquiries` の入力候補：

    * title, description, category_id, requester_user_id, (任意) due_date など
  * `GET /inquiries` の出力候補：

    * id, title, status, category_name, assignee_name, created_at など

**4-2. AIにJSON例を作らせるデモ（15分）**

* プロンプト例：

  ```text
  次のAPIエンドポイントについて、リクエストとレスポンスのJSON例を作ってください。

  1. POST /inquiries
     - 新しい問い合わせを登録する
     - 入力に必要な項目：件名(title)、内容(description)、カテゴリID(category_id)、
       依頼者ユーザーID(requester_user_id)、任意で対応期限(due_date)

  2. GET /inquiries
     - 問い合わせの一覧を取得する
     - 1件あたりの情報として、id, title, status, category_name,
       assignee_name, created_at が含まれていると嬉しいです。

  各エンドポイントごとに、
  - リクエストJSONの例
  - レスポンスJSONの例
  - ステータスコードの例
  を、わかりやすいコメント付きで出力してください。
  ```

* AIが出したJSONを画面表示しながら：

  * キーポイントを指さし解説：

    * 「ここが**フロントから送られる情報**」
    * 「ここが**バックエンドから返ってくる情報**」
    * 「`status: "pending"` のように、人間にも意味がわかる文字列を使う設計も多い」

### 5. AIにバックエンドコードを書かせて“読み方”を学ぶ（30分）

**目的：**
AI生成コードを題材に、「どのURLで、どのテーブルをどう触っているか」を読めるようになる

**5-1. 言語・フレームワークの選択と位置づけ（5分）**

* 例として、以下のどちらかを使用（どちらでも良い想定）：

  * Node.js + Express
  * または Python + FastAPI

* ナレーション例：

  * 「言語やフレームワークは**一例**です。大事なのは、“どのURLがどの処理をしているか”という視点です。」

**5-2. AIにコードを書かせるデモ（15分）**

* プロンプト例（FastAPI例）：

  ```text
  次のAPIを、PythonとFastAPIで実装したサンプルコードを書いてください。

  - POST /inquiries
    - リクエストJSONから、title, description, category_id, requester_user_id, due_date を受け取る
    - データベースの inquiries テーブルに1件追加する想定（実際のDB接続はダミーでOK）

  - GET /inquiries
    - 簡易的に、問い合わせ一覧（id, title, status, category_name, assignee_name, created_at）を返す

  非エンジニアにも読みやすいように、
  - 関数の上に日本語コメントで「何をしている関数か」を書く
  - ダミーデータで良いので、最低限の処理の流れがわかるようにする
  ようにしてください。
  ```

* コードが出てきたら、ポイントを解説：

  * `@app.post("/inquiries")` ← 「この行が“URLとメソッド”を決めている場所です」
  * 関数内で、リクエストボディを受けている行
  * （ダミーでも）新規データを作って返している行
  * 「**どの部分が“DBを触るところ”なのか**にマーカーを引いて説明」

**5-3. “非エンジニアの読み方”のコツ解説（10分）**

* スライドで「3つのチェックポイント」を提示：

  1. **どのURL・メソッドに対応しているか？**

     * `@app.get("/inquiries")` / `router.post("/inquiries")` など
  2. **どのテーブル（エンティティ）を触っているか？**

     * `Inquiry` モデル、`inquiries` テーブル名が出てくる箇所
  3. **入力・出力データの“形”が、設計どおりか？**

     * JSONのキーが第4章で決めたものと合っているか

* ナレーション例：

  * 「コード全部を理解する必要はありません。**“3つのチェックポイント”だけでも押さえれば、エンジニアと意思疎通がかなり楽になります。**」

### 6. 処理フローの図解＆エラー・バリデーションのイメージ（10分）

**目的：**
画面 → API → DB の流れを再度「線」で理解し、エラー時の挙動もざっくり掴む

**6-1. 正常系フローを図で確認（6分）**

* Mermaidやスライドを使って、`問い合わせ登録` のフローを図解：

  1. ユーザーが画面でフォーム入力 → 「送信」クリック
  2. フロントから `POST /inquiries` にJSON送信
  3. バックエンドが受け取って、inquiriesテーブルに挿入
  4. 成功レスポンス（201 Created + JSON）を返す
  5. 画面で「登録完了」表示

* AIにフローの文章化を依頼する簡単デモ：

  ```text
  「問い合わせ登録画面からPOST /inquiriesが呼ばれるまで」の処理フローを、
  非エンジニアにもわかるように5ステップくらいで説明してください。
  ```

**6-2. エラー・バリデーションのイメージ紹介（4分）**

* 例：

  * 必須項目が抜けている → 400 Bad Request
  * 存在しないカテゴリIDを指定 → 400 or 422
  * サーバー側の問題 → 500 Internal Server Error

* ナレーション例：

  * 「詳細な実装はエンジニアの領域ですが、**“どんな時にどんなエラーコードが返ると良いか”を会話できるだけで、設計レビューの質が上がります。**」

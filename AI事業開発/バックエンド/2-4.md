# 第2回「4. 業務データのテーブル化ワーク」ナレーション原稿(40分)

## 4-1. ワークの説明(5分)

---

### 冒頭(30秒)

さて、ここまでで「テーブル」「レコード」「カラム」という基本的な用語、そして「主キー」の役割について理解していただきました。ここからは、いよいよ皆さん自身の業務データを「データベースのテーブル」として整理してみる実践ワークに入っていきます。

このワークの時間は約40分です。最初の5分で全体の進め方を説明し、その後、実際に手を動かしていただく時間も設けています。

### ワークのゴール提示(1分)

それでは、まず今回のワークで目指すゴールを確認しましょう。

画面に表示しているように、このワークのゴールはシンプルです。

「**今、Excelで管理している業務データを、1つのテーブルとして整理してみる**」

これだけです。

難しいSQL文を書くわけでも、複雑なシステムを作るわけでもありません。「自分が日々扱っているデータを、データベース視点で見たらどうなるか」を考えてみる。それがこのワークの目的です。

### 題材の候補紹介(1分30秒)

では、具体的にどんな業務データをテーブル化すればいいのか。画面に3つの候補を出していますので、一緒に見ていきましょう。

まず1つ目、**「顧客管理」**です。
これは多くの企業で必ず扱っているデータですね。顧客リスト、取引先リスト、クライアント情報など、呼び方はいろいろあると思いますが、「誰と」取引しているか、「どんな会社」とやり取りしているか、こうした情報を管理している表が該当します。

2つ目は**「案件管理」**です。
営業案件、商談リスト、プロジェクト一覧など、これも会社によって呼び方は異なりますが、「どんな仕事が進んでいるか」「どの案件がどういう状態か」を追いかけている表のことです。

そして3つ目が**「予約管理」**です。
セミナーの予約、面談の予約、施設の予約など、「いつ・誰が・何を予約したか」を記録している表です。予約システムを使っている会社もあれば、Excelで手作業で管理している会社もあるでしょう。

もちろん、これら以外にも在庫管理、勤怠管理、経費精算など、さまざまな業務データがあると思います。大事なのは、「自分が一番身近に感じる表」を選ぶことです。

実際に今、仕事で使っているExcelファイルがあれば、それをベースに考えていただいて構いません。そのファイルを開いて、「この表をデータベースのテーブルにするなら、どう整理すればいいか」と考えてみてください。

### ワークの進め方の概要(1分30秒)

このワークは、大きく分けて4つのステップで進めていきます。

まず、「**カラムを洗い出すステップ**」を一緒に学びます。ここでは、「1行に何を書きたいか」を決めて、その1件についてどんな情報を持っておきたいかを整理する方法を解説します。

次に、「**よくあるNGな表の例と修正**」を見ていきます。実は、Excelで管理している表の中には、データベースにそのまま持っていくと困る形になっているものも少なくありません。どういうパターンが問題なのか、どう修正すればいいのか、具体例を交えてお話しします。

その後、「**実際に手を動かすワーク**」として、10分間の作業時間を設けています。ここでは一度動画を止めていただいて、紙でもExcelでも、メモアプリでも構いませんので、実際にご自身の業務データのテーブルを設計してみてください。

そして最後に、「**AIにテーブル定義へ変換させるデモ**」をお見せします。皆さんが日本語で整理した項目を、AIがどのようにデータベースのテーブル定義書に変換してくれるのか、実際のプロンプトと出力結果をお見せしながら解説します。

では、さっそく最初のステップ、「カラムを洗い出す」ところから始めていきましょう。

## 4-2. カラムを洗い出すステップ(10分)

---

### カラムを洗い出す手順の説明(2分30秒)

それでは、業務データをテーブル化する最初のステップとして、「カラムを洗い出す」方法を見ていきましょう。

ここでの作業は、非常にシンプルです。たった2つのことを決めるだけです。

**1つ目は、「1行に何を書きたいか」を決める**

これは、先ほどお話しした「1行=1件」の考え方そのものです。たとえば、顧客管理の表であれば「1行=1人の顧客」ですよね。案件管理なら「1行=1件の案件」、予約管理なら「1行=1件の予約」という具合です。

この「1行が何を表すのか」をまず明確にしてください。これが決まらないと、カラムを考えることができません。

**2つ目は、その1件について、どんな情報を持っておきたいかを書き出す**

1行に何を書くかが決まったら、次はその1件について「どんな項目が必要か」を考えます。

たとえば、顧客管理の場合で考えてみましょう。
1行が1人の顧客を表すなら、その顧客について何の情報を持っておきたいでしょうか？

まず、当然「顧客名」は必要ですよね。個人なのか法人なのかで変わるかもしれませんが、名前は必須です。

次に、法人のお客様が多いなら「会社名」も欲しいでしょう。場合によっては「部署名」や「役職」も必要かもしれません。

連絡先として、「メールアドレス」や「電話番号」も大事です。最近はメールが主流かもしれませんが、電話番号も念のため持っておきたい、という会社は多いと思います。

住所はどうでしょうか。全住所を持つ必要がある場合もあれば、「都道府県」だけで十分という場合もあります。これは業務によって変わります。

それから、「担当営業」や「担当者」の情報。誰がこの顧客を担当しているかを記録しておくと、後で「この顧客は誰が対応しているんだっけ?」と探さなくて済みます。

さらに、「ステータス」も重要です。この顧客は「見込み客」なのか、「既存顧客」なのか、「休眠中」なのか、「失注」なのか。こういった状態を表す項目があると、顧客の管理がしやすくなります。

最後に、「メモ」や「備考」といったフリーテキストの欄も、実務では重宝します。定型的な項目では表現しきれない情報を残しておく場所ですね。

このように、「1人の顧客について、何を知っておきたいか」を洗い出していくと、それがそのまま「カラム」のリストになるわけです。

### テンプレートの説明(3分)

では、画面に実際のテンプレートを表示しますので、一緒に見ていきましょう。

```
テーブル名:customers(顧客)

1行=1人の顧客

欲しいカラム(項目):
- customer_id(顧客ID)
- name(氏名)
- company_name(会社名)
- email(メールアドレス)
- phone(電話)
- prefecture(都道府県)
- sales_person(担当営業)
- status(ステータス:見込み/受注/失注 等)
- notes(備考メモ)
```

このテンプレートを上から順に見ていきましょう。

まず一番上、**「テーブル名:customers(顧客)」**とあります。
ここでは、このテーブルが何を管理するためのものなのかを明記しています。英語で`customers`、日本語で「顧客」と書いていますね。

テーブル名は、後でデータベースを構築するときには英語で書くことが一般的ですが、今の段階では日本語で書いても全く問題ありません。大切なのは「このテーブルが何のためにあるか」を明確にすることです。

次に、**「1行=1人の顧客」**という記述があります。
これは先ほどお話しした「1行が何を表すか」を明示しているものです。このテーブルでは、1行が1人の顧客を表す、ということを最初に宣言しているわけです。

そして、その下に**「欲しいカラム(項目)」**のリストが並んでいます。

最初に出てくる`customer_id(顧客ID)`、これが主キーです。前のセクションで学んだように、各顧客を一意に識別するためのIDですね。

その後は、`name`(氏名)、`company_name`(会社名)、`email`(メールアドレス)、`phone`(電話)と続いています。これらは、先ほど口頭で挙げた項目と同じものです。

`prefecture`(都道府県)は、住所情報の一部ですね。全住所ではなく、都道府県だけを持つという選択をしている例です。

`sales_person`(担当営業)は、この顧客を担当している営業担当者の名前、あるいは担当者IDを入れる欄です。

`status`(ステータス)は、顧客の状態を表すカラムです。ここでは「見込み/受注/失注」といった値が入ることを想定しています。

最後の`notes`(備考メモ)は、先ほど触れたフリーテキストの欄ですね。

こんな風に、「何のテーブルか」「1行が何を表すか」「どんな項目があるか」を箇条書きで整理すると、データベースのテーブル設計の第一歩が完成します。

### ポイントの強調(2分30秒)

ここで、このステップで特に意識してほしいポイントを2つお伝えします。

**ポイント1:まずは日本語で書いてOK**

画面のテンプレートでは、`customer_id`や`company_name`といった英語の名前も併記していますが、最初から英語で考える必要はありません。

「顧客ID」「会社名」「メールアドレス」といった日本語で書いて構いません。英語のカラム名にするのは、後からAIに手伝ってもらうこともできますし、エンジニアと一緒に決めてもいいでしょう。

今の段階で大切なのは、「どんな情報が必要か」を日本語で明確にすることです。英語が苦手だからといって、ここで手が止まってしまうのはもったいないですからね。

**ポイント2:「1行=1件」という感覚を常に意識する**

これは本当に大事なポイントです。

データベースのテーブルを設計するとき、必ず「1行=1件」の原則を守ってください。

1行が「1人の顧客」を表すなら、その行には1人分の情報だけを入れる。2人分の情報を1行に詰め込んだり、1人の情報を複数行に分散させたりしない。

これは当たり前のように聞こえるかもしれませんが、実際のExcelを見てみると、この原則が崩れている表が意外と多いんです。次のセクションで、そういった「NGな表」の例を見ていきますが、まずはこの「1行=1件」という感覚をしっかりと頭に入れておいてください。

### 案件管理と予約管理の簡単な例(2分)

では、顧客管理以外の例も簡単に見ておきましょう。

たとえば**案件管理**の場合。

テーブル名は`projects`(案件)などになるでしょう。
1行=1件の案件、ですね。

欲しいカラムとしては:
- 案件ID(`project_id`)
- 案件名(`project_name`)
- 顧客ID(`customer_id`)- これは先ほどの顧客テーブルとの紐付けに使います
- 担当者(`person_in_charge`)
- ステータス(`status`)- 提案中/受注/完了/失注など
- 開始予定日(`start_date`)
- 終了予定日(`end_date`)
- 受注金額(`amount`)
- 備考(`notes`)

こんな項目が考えられます。

次に**予約管理**の場合。

テーブル名は`reservations`(予約)などでしょう。
1行=1件の予約、です。

欲しいカラムとしては:
- 予約ID(`reservation_id`)
- 予約者名(`customer_name`)
- メールアドレス(`email`)
- 電話番号(`phone`)
- 予約日時(`reservation_datetime`)
- 予約内容(`reservation_type`)- セミナーA、面談、施設利用など
- 人数(`number_of_people`)
- ステータス(`status`)- 予約済み/キャンセル/完了など
- 備考(`notes`)

このように、管理したい対象が変わっても、「1行=1件」「必要な項目を洗い出す」という考え方は共通しています。

## 4-3. よくある「NGな表」の例と修正(10分)

---

### このセクションの目的(30秒)

さて、ここからは、実際によく見かける「データベースとしては問題がある表」の例を見ていきます。

Excelで長年使ってきた表をそのままデータベースに持っていこうとすると、うまくいかないケースがあります。なぜなら、「人間が見て分かりやすい表」と「データベースとして扱いやすい表」は、必ずしも一致しないからです。

どんなパターンが問題なのか、どう修正すればいいのか、3つの代表的な例を見ていきましょう。

### NG例1:1つのセルに複数の値が入っている(3分30秒)

まず1つ目のNGパターンです。画面を見てください。

```
顧客ID | 顧客名 | 取引先企業
001   | 田中太郎 | A社/B社/C社
002   | 鈴木花子 | D社
```

このテーブルの「取引先企業」というカラムに注目してください。

田中太郎さんの行を見ると、「A社/B社/C社」と、スラッシュで区切られた3つの企業名が1つのセルに入っています。

これは、Excelでは割とよく見る形ですよね。「この人は3社と取引がある」ということを、1つのセルにまとめて書いておく。見た目にはコンパクトで分かりやすいかもしれません。

でも、データベースの世界では、これは大きな問題です。

なぜかというと、**検索や集計が非常に難しくなるから**です。

たとえば、「A社と取引がある顧客を全員抽出したい」と思ったとき、このままでは簡単には抽出できません。「取引先企業」のカラムを見ても、「A社/B社/C社」という文字列があるだけで、「A社」だけを取り出すのが困難なんです。

また、「B社と取引がある顧客は何人いるか」を数えたいときも、やはり同じ問題が起きます。

では、どう修正すればいいのでしょうか。

答えは、**「1セル=1つの値」にする**ことです。

具体的には、テーブルを分けます。

```
顧客テーブル:
顧客ID | 顧客名
001   | 田中太郎
002   | 鈴木花子

顧客-企業 関連テーブル:
顧客ID | 企業名
001   | A社
001   | B社
001   | C社
002   | D社
```

このように、顧客情報は「顧客テーブル」に、顧客と企業の関係は別の「関連テーブル」に分けます。

こうすることで、田中太郎さんが3社と取引があることは、関連テーブルの3行で表現されます。1行に1つの企業名しか入らないので、「A社と取引がある顧客」を検索するのも、「B社と取引がある顧客の数」を数えるのも簡単になります。

これが、**正規化**と呼ばれる考え方の一部です。今日は正規化という用語を覚える必要はありませんが、「1セルに複数の値を詰め込まない」という原則だけは、ぜひ覚えておいてください。

### NG例2:列の意味がバラバラ(3分)

次に、2つ目のNGパターンを見てみましょう。

```
顧客ID | 顧客名 | 情報
001   | 田中太郎 | 東京都渋谷区
002   | 鈴木花子 | 営業部で働いている
003   | 佐藤次郎 | 2024年入会
```

この表の「情報」というカラムに注目してください。

田中太郎さんの行には「東京都渋谷区」と住所が入っています。
鈴木花子さんの行には「営業部で働いている」と所属部署の情報が入っています。
佐藤次郎さんの行には「2024年入会」と登録日の情報が入っています。

同じ「情報」というカラムなのに、行によって入っている内容の意味が全然違いますね。

これも、Excelでは「とりあえずメモしておきたいことを書く欄」として使われることがありますが、データベースとしては問題です。

なぜなら、**カラムには一貫した意味の値が入っていることが前提**だからです。

「住所」のカラムなら、すべての行に住所が入る。「部署」のカラムなら、すべての行に部署名が入る。これが基本です。

もし、住所も部署も登録日も全部必要なら、それぞれ別のカラムとして持つべきです。

```
修正後:
顧客ID | 顧客名 | 住所        | 部署  | 登録日
001   | 田中太郎 | 東京都渋谷区 | NULL  | NULL
002   | 鈴木花子 | NULL        | 営業部 | NULL
003   | 佐藤次郎 | NULL        | NULL  | 2024-01-01
```

このように、カラムを分けます。情報がない部分は`NULL`(データなし)にしておけばいいんです。

「でも、そうすると空欄がいっぱいできて無駄じゃないですか?」と思うかもしれません。

確かに、見た目には空欄が多くなります。でも、データベースは空欄があっても問題なく動きますし、むしろ「各カラムの意味が明確」である方が、後々の検索や集計、システムとの連携がスムーズになります。

カラムごとに意味を統一する。これがデータベース設計の大原則です。

### NG例3:1行が「1件」ではなく、複数の意味を持っている(3分)

最後に、3つ目のNGパターンです。これは少し複雑なので、ゆっくり見ていきましょう。

```
顧客ID | 顧客名 | 2023年購入額 | 2024年購入額 | 2025年購入額
001   | 田中太郎 | 100,000    | 150,000    | 200,000
002   | 鈴木花子 | 80,000     | 90,000     | 100,000
```

この表は、顧客ごとに年別の購入額を記録しています。一見、整然としていて問題なさそうに見えますよね。

でも、よく考えてみてください。

今は2023年、2024年、2025年の3年分のカラムがありますが、2026年が来たらどうしますか? また新しいカラムを追加しますか? 10年経ったら、カラムが10個以上になってしまいます。

さらに、「2024年の購入額が10万円以上の顧客を抽出したい」といった検索をするとき、この形式だとやりにくいんです。なぜなら、年ごとにカラムが分かれているため、SQLで書くときに「2024年購入額 >= 100,000」という条件を指定しなければならず、年が変わるたびに条件を変える必要があるからです。

では、どうすればいいのか。

答えは、**「1行=1件の購入実績」**として、テーブルを再設計することです。

```
修正後:
購入実績ID | 顧客ID | 年   | 購入額
00001    | 001   | 2023 | 100,000
00002    | 001   | 2024 | 150,000
00003    | 001   | 2025 | 200,000
00004    | 002   | 2023 | 80,000
00005    | 002   | 2024 | 90,000
00006    | 002   | 2025 | 100,000
```

このように、年ごとに1行を作ります。

こうすることで、「2024年の購入額が10万円以上」という条件は、「年=2024 AND 購入額>=100,000」というシンプルな検索で実現できます。

また、新しい年が来ても、カラムを追加する必要はありません。新しい行を追加していくだけです。

このパターンは、「時系列データ」を扱うときに特によく出てきます。月別の売上、日別のアクセス数、年別の在庫数など、時間軸でデータを持ちたい場合は、「1行=1つの時点のデータ」として設計すると、後々扱いやすくなります。

### まとめ:修正の考え方(1分)

ここまで3つのNGパターンを見てきました。最後に、修正の考え方をまとめておきましょう。

**修正のポイント1:1セル=1つの意味のある値**

複数の値をスラッシュやカンマで区切って1つのセルに入れない。それぞれ別の行、または別のテーブルに分ける。

**修正のポイント2:1行=1つの「出来事」や「対象」**

1行が表すものを明確にする。顧客なら1行=1人の顧客。購入実績なら1行=1回の購入。時系列データなら1行=1つの時点。

この2つの原則を守ると、データベースとして扱いやすい表になります。

もちろん、最初から完璧に作れなくても大丈夫です。まずは「こういう考え方があるんだな」と理解していただければ十分です。実際に設計してみて、AIやエンジニアと相談しながら、少しずつ修正していけばいいんですから。

## 4-4. 実際に手を動かすワーク(10分)

---

### ワークの案内(1分30秒)

さて、ここまでで、テーブル化の基本的な考え方と、よくある失敗パターンを見てきました。

ここからは、皆さん自身で実際に手を動かしていただく時間です。

このワークは**10分間**です。

動画をここで一度止めていただいて、10分間、ご自身の業務データをテーブルとして設計してみてください。

使うツールは何でも構いません。紙とペンでも、Excelでも、Wordでも、スマホのメモアプリでも、Notionでも、何でもOKです。大事なのは、「書き出してみる」ことです。

### やること:3つのステップ(2分)

では、具体的に何をするのか。3つのステップで進めていきましょう。

**ステップ1:「1行=何か」を決める**

まず、自分が扱っているデータの中から1つ選んで、「1行が何を表すか」を決めてください。

顧客管理なら「1行=1人の顧客」
案件管理なら「1行=1件の案件」
予約管理なら「1行=1件の予約」

といった具合です。

もし複数の表を管理している場合は、その中で一番「これはよく使う」「これが一番大事」と思うものを1つ選んでください。1つに絞ることで、10分という短い時間でも作業が完結しやすくなります。

**ステップ2:持っておきたい項目(カラム)を箇条書きにする**

「1行=何か」が決まったら、その1件について、どんな情報を持っておきたいかを箇条書きにしてください。

最低でも5項目、できれば10項目くらい挙げてみるといいでしょう。

このとき、すべて日本語で書いて構いません。「顧客名」「メールアドレス」「電話番号」「住所」「担当者」「ステータス」「登録日」「備考」…といった感じです。

もし、今使っているExcelファイルがあれば、その列見出しをそのまま書き出してもいいですし、「この項目も追加したいな」と思うものがあれば、それも加えてください。

**ステップ3:可能であれば「主キーとなるID」も1つ決めてみる**

余裕があれば、このテーブルの主キー、つまり「各行を一意に識別するためのID」も考えてみてください。

「顧客ID」「案件ID」「予約ID」など、「◯◯ID」という名前にすることが多いです。

もし今のExcelに既にそういうID列があれば、それを主キーとして使えます。もしなければ、「新しく追加するならこういうIDが必要だな」と考えてみてください。

## 4-5. AIにテーブル定義へ変換させるデモ(5分)

---

### このセクションの目的(30秒)

さて、ワークで皆さんが書き出した「日本語の項目リスト」を、AIに渡すと、どんな風に「データベースのテーブル定義」に変換してくれるのか。

ここからは、実際のプロンプトと、AIの出力結果をお見せしながら、その流れを見ていきましょう。

このデモを見ることで、「ああ、自分が書いたメモも、こんな風にAIに整理してもらえるんだ」というイメージが湧くはずです。

### 実演プロンプトの紹介(1分30秒)

では、画面にプロンプトを表示しますので、一緒に見ていきましょう。

```
以下は、ある会社の顧客管理Excelで使っている項目です。

- 顧客名
- 会社名
- 部署
- 役職
- メールアドレス
- 電話番号
- 都道府県
- 担当営業
- ステータス(見込み/受注/失注)
- 備考メモ

これをデータベースの「顧客テーブル」として、
テーブル名・カラム名(英語)・型・説明を含むテーブル定義書にしてください。
主キーのカラムも1つ提案してください。
```

このプロンプトのポイントを解説します。

まず、「以下は、ある会社の顧客管理Excelで使っている項目です」という前置きをしています。これによって、AIに「今からリストアップする内容は、実務で使っている項目なんだ」という文脈を伝えています。

次に、日本語で箇条書きにした項目をそのまま貼り付けています。

そして、「これをデータベースの『顧客テーブル』として、テーブル名・カラム名(英語)・型・説明を含むテーブル定義書にしてください」と指示しています。

ここで「カラム名(英語)」と書いているのがポイントです。日本語で渡した項目を、AIが英語のカラム名に変換してくれます。

さらに、「主キーのカラムも1つ提案してください」と追加で依頼しています。こうすることで、AIが「customer_id」のような主キーを自動で提案してくれます。

では、このプロンプトをAIに投げると、どんな結果が返ってくるのか、見てみましょう。

### AIの出力例を見る(2分)

AIからの出力は、こんな感じになります。

```
【テーブル定義書】

テーブル名:customers

説明:顧客情報を管理するテーブル

| カラム名          | 型           | 説明                            | 制約          |
|-------------------|--------------|--------------------------------|---------------|
| customer_id       | INT          | 顧客ID(主キー)                 | PRIMARY KEY, AUTO_INCREMENT |
| name              | VARCHAR(100) | 顧客名                         | NOT NULL      |
| company_name      | VARCHAR(100) | 会社名                         |               |
| department        | VARCHAR(50)  | 部署                           |               |
| position          | VARCHAR(50)  | 役職                           |               |
| email             | VARCHAR(100) | メールアドレス                 |               |
| phone             | VARCHAR(20)  | 電話番号                       |               |
| prefecture        | VARCHAR(20)  | 都道府県                       |               |
| sales_person      | VARCHAR(50)  | 担当営業                       |               |
| status            | VARCHAR(20)  | ステータス(見込み/受注/失注)   |               |
| notes             | TEXT         | 備考メモ                       |               |

主キー:customer_id
- 自動採番される顧客IDで、各顧客を一意に識別します。
```

いかがでしょうか。

私たちが日本語で箇条書きにしただけの項目が、こんな風にきれいな「テーブル定義書」に変わりました。

それぞれのカラムに英語名が付けられ、「型」(INT、VARCHAR、TEXTなど)も提案されています。さらに、「制約」という欄には、主キーであることや、NOT NULL(空にしてはいけない)といった情報も書かれています。

「型」というのは、そのカラムにどんな種類のデータが入るかを示すものです。たとえば、`INT`は整数、`VARCHAR`は文字列、`TEXT`は長い文章、といった具合です。この辺りは、今は深く理解しなくても大丈夫です。「ああ、こういう情報も必要なんだな」くらいに思っていただければ十分です。

### 補足説明とメッセージ(1分)

ここで大事なのは、**「人間側は"何を管理したいか"さえ言語化できれば、AIがデータベースの形にしてくれる」**ということです。

皆さんは、カラム名を英語で書く必要も、型を決める必要も、制約を考える必要もありません。

まずは、「こういう情報を持っておきたい」というリストを日本語で作る。それをAIに渡せば、あとはAIが整形してくれます。

もちろん、AIの提案が100%完璧とは限りません。実際にシステムを作るときには、エンジニアと相談しながら微調整することもあるでしょう。

でも、「ゼロから全部自分で考える」のと、「AIが作った叩き台を見ながら話す」のとでは、作業のスピードも、議論の質も、まったく違います。

今日のゴールは、まさにここです。

**「自分の業務データを『何を管理したいか』という形で言語化できること」**

これができれば、AIの力を借りて、テーブル設計ができるんです。

そして、このテーブル設計ができれば、次の第3回で学ぶSQLも、第4回で学ぶAPIも、すべてこのテーブルを基盤にして理解できるようになります。
